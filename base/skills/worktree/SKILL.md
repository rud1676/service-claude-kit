# 워크트리 기반 구현·PR 절차 (공용)

상위 워크플로우(jiraticket 등)가 **분석을 끝내고 "수정 진행" 승인을 받은 시점**부터, 메인 체크아웃을 건드리지 않고 별도 워크트리 폴더 안에서만 수정·검증·커밋·PR을 수행하는 공통 절차다.

이 스킬은 **메커니즘만** 정의한다. 아래 값은 **호출하는 상위 스킬이 결정해서 넘겨준다.**

| 호출자가 넘기는 값 | 설명 |
|---|---|
| `<티켓번호>` | 예: `PROJ-1712`. **브랜치명·커밋·PR에 그대로 쓴다.** 티켓번호가 없으면 사용자에게 묻지 말고 이슈 트래커로 직접 생성한다(아래 "티켓 자동 생성" 참고). 이슈 트래커를 안 쓰는 프로젝트면 짧은 작업 슬러그(예: `fix-login-toast`)로 대체한다. |
| `<type>` | 커밋 type. 변경 성격에 맞게 `fix`/`feat`/`refactor` 등 |
| 수정 대상 repo 목록 | `repository/` 아래 실제 repo 중 1개 이상 |
| 변경 요지 | 무엇을 어떻게 고칠지 (상위 스킬의 분석 결과) |

> **⚠️ 브랜치 식별자 필수 — 없으면 자동 생성**: 워크트리 작업은 **항상 티켓번호(또는 작업 슬러그)를 브랜치명으로** 사용한다. 이슈 트래커를 쓰는 프로젝트에서 티켓번호가 명시되지 않으면 **묻지 말고 이슈 트래커로 직접 생성**한다.
>
> **티켓 자동 생성 절차 (Jira 예시 — 이슈 트래커에 맞게 조정)**:
> 1. `getAccessibleAtlassianResources` → cloudId 확인 (`{JIRA_CLOUD_ID}`)
> 2. `createJiraIssue` 호출:
>    - `cloudId`: `{JIRA_CLOUD_ID}`
>    - `projectKey`: `{PROJECT_KEY}`
>    - `issueTypeName`: `작업`(또는 Task)
>    - `summary`: 작업 내용을 한 줄로 요약
>    - `assignee_account_id`: `{DEFAULT_ASSIGNEE_ID}`
> 3. 생성된 티켓번호(예: `{PROJECT_KEY}-1802`)를 브랜치명으로 사용
> 4. 생성된 티켓 URL(`https://{JIRA_HOST}/browse/{PROJECT_KEY}-XXXX`)을 사용자에게 알린다

> **전제(레포 구조)**: 실제 git repo는 `repository/` 아래에 있고 각각 **독립된 git repo**다. (스타터킷의 워크스페이스 규약)
> 브랜치·커밋·워크트리는 반드시 **해당 repo 디렉토리 안**에서 실행한다.

> **Tip**: 도구 호출이 많으므로 **Shift+Tab**으로 auto-accept를 켜는 걸 권장.

> **📂 변경 파일은 `file://` 마크다운 링크로 제시 (공용 규칙)**: 사용자에게 작업한 파일 목록을 보여줄 때는 **클릭 가능한 마크다운 링크**로 출력한다. 사용자가 검토하는 건 보통 **워크트리 안에서 수정된 파일**이므로, 링크 대상은 메인 체크아웃이 아니라 **워크트리의 절대경로**로 건다.
>
> - 형식: `[<repo 기준 상대경로>](file://<워크트리 절대경로>)`
> - ⚠️ **`:<줄번호>` 접미사 금지**: 일부 에디터(원격 Zed 등)는 `file://<절대경로>:42`처럼 줄번호를 붙이면 `:42`까지 포함한 문자열 전체를 경로로 인식해 빈 파일을 열어버린다. 링크는 **항상 줄번호 없이 파일 경로까지만** 걸고, 특정 줄은 링크 아래 "OO번째 줄 근처"로 병기하거나 스니펫을 함께 보여준다.
> - 절대경로에 공백·특수문자가 있으면 URL 인코딩한다(공백 → `%20`).
> - 예시:
>   ```
>   변경 파일:
>   - [src/pages/Home.tsx](file://<절대경로>/repository/<front-repo>-worktrees/PROJ-1712/src/pages/Home.tsx) (88행 근처)
>   ```
> - 2단계(변경 파일 요약)·7단계(PR 완료 표)·9단계(동작 확인 체크리스트) 등 **파일을 언급하는 모든 보고에서 이 링크 형식을 쓴다.**
> - 이 형식도 안 열리면(클라이언트가 `file://`를 못 여는 경우) 평문 절대경로로 되돌린다.

아래 표기에서 `<티켓번호>`는 호출자가 넘긴 값(예: `PROJ-1712`)으로, `<repo>`는 실제 repo 이름으로 치환한다.

## 1. 워크트리 생성 (작업공간 분리)

수정 대상으로 확정된 **각 repo마다** 형제 경로에 티켓번호로 워크트리를 만든다.
(워크트리는 repo 내부가 아니라 형제 경로 `../<repo>-worktrees/<티켓번호>/`에 둔다 — git 추적이 꼬이지 않게.)

> ⚠️ **워크트리 생성 전 항상 `origin/main` 최신화**: 로컬 `main`은 뒤처져 있을 수 있으므로, 워크트리를 만들기 전에 반드시 `git fetch origin main`으로 원격 최신을 받고, **베이스를 `origin/main`으로 지정해 워크트리를 생성**한다. (로컬 `main` 체크아웃을 이동/갱신할 필요 없이 항상 최신에서 시작된다.)

```bash
cd repository/<repo>
git fetch origin main
git worktree add ../<repo>-worktrees/<티켓번호> -b <티켓번호> origin/main
```

- 여러 repo에 걸치면 각 repo에서 **동일 티켓번호**로 워크트리를 만든다.
- 동일 브랜치가 이미 있으면 `-b` 없이 기존 브랜치로 add 하거나 사용자에게 알린다.
- 이후 파일 수정·lint·커밋은 모두 **워크트리 폴더 안**에서 한다 (원본 repo 폴더가 아니라).
- 어느 repo에 어떤 워크트리(폴더 경로·브랜치)를 만들었는지 사용자에게 명시한다.

### ⚠️ node_modules 연결 (JS 프로젝트 — 워크트리 필수 선행 작업)

**git worktree로 만든 폴더에는 `node_modules`가 없다.** (gitignore라 체크아웃에 안 따라오고, 워크트리끼리 공유되지 않는다.)
이 상태에서 lint/prettier/build를 돌리면 `npx`가 엉뚱한 최신 버전을 새로 설치하거나 모듈을 못 찾아 실패한다.
그래서 **코드 수정 전에 메인 체크아웃의 `node_modules`를 워크트리에 심볼릭 링크**해 둔다. (install 재실행보다 빠르고, 의존성이 동일하면 안전)

```bash
ln -s /절대경로/repository/<repo>/node_modules \
      /절대경로/repository/<repo>-worktrees/<티켓번호>/node_modules
```

- 메인 repo에 `node_modules`가 없으면 먼저 메인에서 `install` 후 링크하거나, 워크트리에서 직접 install 한다.
- 심볼릭 링크는 gitignore 대상이라 커밋에 포함되지 않으니 그대로 둬도 된다.

> ⚠️ **프레임워크에 따라 심볼릭 링크가 깨질 수 있다.** 예: Next.js는 symlinked `node_modules`에서 `Cannot find module` 오류가 난다. 그런 repo는 링크 대신 `install --frozen-lockfile`을 직접 돌린다. (Vite 등은 symlink를 안전하게 처리한다.) 어느 repo가 어느 방식인지는 아래 커스터마이징 주석에 적어둔다.

### ⚠️ gitignore된 env 파일 연결 (워크트리 필수 선행 작업 — 항상)

**`node_modules`처럼 gitignore된 env 파일(특히 `.env.local`)도 워크트리에 따라오지 않는다.** 추적되는 env(`.env` 등)만 체크아웃에 딸려온다.
`.env.local`에는 피처 플래그·로컬 백엔드 주소 등 **동작에 필수인 값**이 들어 있어, 없으면 lint/build는 통과해도 dev 서버나 일부 코드 분석에서 빈 값으로 떨어진다.
그래서 **node_modules를 링크하는 같은 시점(코드 수정 전)에, 메인 체크아웃의 gitignore된 env를 워크트리에 항상 심볼릭 링크**해 둔다. (서버를 띄울지와 무관하게 항상 한다.)

```bash
ln -sf /절대경로/repository/<repo>/.env.local \
       /절대경로/repository/<repo>-worktrees/<티켓번호>/.env.local
```

- 각 repo에서 **추적되는 env(체크아웃에 딸려옴)** 와 **gitignore된 env(링크 필요)** 가 무엇인지는 프로젝트마다 다르다. 아래 커스터마이징 주석에 repo별로 매핑해 둔다.
- 메인에 해당 env 파일이 없으면 링크할 것도 없다.
- 심볼릭 링크라 gitignore 대상 → 커밋/diff에 포함되지 않으니 그대로 둔다.

## 2. 코드 수정 (워크트리 안에서)

**중요**: 이후 모든 수정은 메인 체크아웃이 아니라 위에서 만든 **워크트리 폴더 경로** 기준으로 한다.
(예: `repository/<repo>/src/...`가 아니라 `repository/<repo>-worktrees/<티켓번호>/src/...`)

- 상위 스킬의 분석 결과(변경 요지)를 워크트리 폴더 안에서 직접 수정한다.
- 복잡하면 TaskCreate로 작업을 분해한다.
- 변경된 파일 목록과 변경 내용 요약을 사용자에게 보여준다. **이때 각 파일은 위 "변경 파일은 `file://` 마크다운 링크로 제시" 규칙대로 출력**한다.

## 3. 검증 (워크트리 안에서 — 한 번에)

검증도 **워크트리 폴더 안에서** 실행한다. **1단계에서 node_modules를 링크해 둔 상태여야 한다.**
`npx`는 로컬에 없으면 엉뚱한 버전을 설치하므로, 링크된 로컬 바이너리(`./node_modules/.bin/...`)를 직접 호출한다.

> ⚡ **왕복을 줄이려고 prettier → eslint → build 를 한 Bash 로 묶어 1왕복에 돌린다.**
> - **prettier·eslint 는 바뀐 파일만** 대상으로 한다(빠르고 충분).
> - **build 는 반드시 전체로 돌린다** — build 는 전체 타입체크/번들이라 "바뀐 파일만"이 성립하지 않는다. 일부만 돌리면 A 를 고쳐 B 가 깨진 걸 못 잡고 **false-green** 이 난다.
> - **build 로그는 통째로 컨텍스트에 담지 않는다**(수천 줄 → 캐시읽기 폭증). 파일로 빼고, 실패했을 때만 에러 요지(파일:줄)만 뽑아 본다.

```bash
cd repository/<repo>-worktrees/<티켓번호>
BUILD_LOG=$(mktemp /tmp/build-<티켓번호>-XXXX.log)
./node_modules/.bin/prettier --write "{바뀐 파일 경로}" \
  && ./node_modules/.bin/eslint "{바뀐 파일 경로}" \
  && ( yarn build > "$BUILD_LOG" 2>&1 \
        && echo "BUILD OK" \
        || { echo "BUILD FAILED — 에러 요지:"; grep -iE "error|failed|cannot|expected|✗" "$BUILD_LOG" | head -n 40; } )
```

- 빌드 산출물이 없는 repo(백엔드 등)는 build 대신 프로젝트 CLAUDE.md 의 `lint` + `prettier` 루프를 따른다.
- 에러가 나면 **고칠 것을 모아 한 번에 수정**하고, 위 한 줄을 그대로 재실행한다. 에러 0 될 때까지 반복하되, **이미 읽은 파일은 다시 읽지 말고** 컨텍스트에 있는 내용으로 고친다.
- 모두 통과하면 다음 단계(4. 변경요약 + 자가검토 게이트)로 진행한다.

## 4. 변경요약 + 자가 검토 게이트 (워크트리 안에서 — 사람 개입 1곳)

검증(3단계)이 통과하면 곧장 커밋하지 않고, **자가 검토를 1회 돌린 뒤 변경요약과 findings 를 한 번에 제시하고 멈춘다.** 무엇을 고칠지는 **사람이 정한다** — 자동 재검토 루프는 없다.

> ⚙️ **왜 자동 루프를 없앴나**: 룰 매칭은 오탐이 섞여, 자동으로 "다 고치면" 멀쩡한 코드를 건드려 churn/회귀가 난다. 게다가 재수정→전체 재검증→재호출 루프가 대화 후반(컨텍스트 최대)에서 돌아 캐시읽기 비용이 가장 크다. 진짜 리뷰는 PR 에서 사람이 하므로, 여기서는 **1패스 조언 + 사람 선택**으로 끝낸다.

### 4-1. 자가 검토 1회

검증 통과 직후 **`reviewer` 서브에이전트를 딱 1번** 호출한다(스타터킷 기본 리뷰어). Agent tool 로 아래처럼 부른다:

```
Agent({ subagent_type: 'reviewer', description: '워크트리 변경 리뷰', prompt: `
아래 워크트리의 변경(git diff)을 리뷰해줘. 코드는 고치지 말고 findings 만 심각도 순으로 보고해줘.
작업공간 경로: <이번 워크트리 절대경로>
` })
```

- `reviewer`는 VERDICT/FINDINGS 만 반환하고 코드를 고치지 않는다(읽기 전용). worktree 는 **재호출하지 않는다** — findings 는 사람에게 넘길 뿐이다.
- 프로젝트에 repo별 리뷰 룰 문서(예: `AGENTS.md`, `FRONT-REVIEW.md`)나 전용 self-review 스킬이 있으면 아래 커스터마이징 주석에 적어두고 여기서 그걸 대신 호출한다.

### 4-2. 변경요약 + findings 를 한 번에 제시하고 멈춘다

변경 파일 표와 findings 를 **한 화면에** 제시한다. findings 는 **심각도로 분류**해, 사람이 한마디로 고를 수 있게 한다.

```
변경 파일:
| 파일 | 변경 | 내용 |
|---|---|---|
| [src/pages/Home.tsx](file://<워크트리 절대경로>/src/pages/Home.tsx) | +12/-3 | 컬럼 추가 |

자가 검토 (VERDICT: REQUEST_CHANGES)
🐛 버그성 (고치는 걸 권장)
  1. api.js:42 — 응답이 없을 때 null 참조 가능
💬 스타일·권고 (선택)
  1. Home.tsx:88 — 매직넘버 상수화 권장
```

- 파일 경로는 공용 규칙대로 **`file://` 마크다운 링크**로 건다.
- "변경"은 `git diff --stat`으로 파일별 +추가/-삭제 라인수를 뽑는다. "내용"은 커밋 메시지 수준 1줄.
- findings 는 **🐛 버그성 / 💬 스타일·권고** 두 묶음으로 나눈다. VERDICT 가 APPROVE 면 "자가 검토 통과, 지적 없음" 한 줄만.
- 표·목록 아래 안내: `고칠 항목을 골라주세요 (예: "버그성만 고쳐" / "1,3번 고쳐" / "그냥 진행"). 고르신 것만 반영하고 커밋합니다.`
- **여기서 멈춘다.** 사람의 선택이 오기 전에는 수정·커밋하지 않는다.

### 4-3. 선택분 반영 → 재검증 → 커밋

- 사람이 지정한 항목**만** 수정한다(이미 읽은 파일은 다시 읽지 않고 컨텍스트 내용으로 고친다).
- 수정 후 **3단계 검증 한 줄을 재실행**해 통과시킨다. **리뷰어는 다시 부르지 않는다.**
- 사람이 "그냥 진행"이면 수정 없이 바로 넘어간다.
- 통과하면 **6단계(커밋)**로 진행한다. (로컬에서 직접 띄워 확인하려면 그 전에 5단계.)

## 5. (선택) 로컬에서 직접 띄워 동작 확인

lint/build가 통과해도 "실제로 화면·API가 의도대로 도는지"는 직접 띄워봐야 안다. **사용자가 "로컬에서 띄워줘 / 테스트해보고 싶다"고 할 때** 이 단계를 한다. 워크트리는 메인 체크아웃과 격리돼 있어 그냥 dev 를 돌리면 안 도는 함정이 있다 — 아래를 순서대로 챙긴다.

### 5-1. env 파일 (1단계에서 이미 링크됨 — 확인만)

gitignore된 env는 **1단계에서 이미 워크트리에 심볼릭 링크**해 뒀다. 여기서는 빠진 게 없는지 확인만 한다. 1단계를 건너뛰고 들어온 경우엔 1단계의 링크 명령을 지금 실행한다.

### 5-2. 병렬로 여러 워크트리를 동시에 띄우는 규칙 (슬롯 포트)

여러 워크트리를 **동시에 띄워 각각의 URL로 같이 확인**하고 싶을 때, 같은 repo의 dev 서버가 같은 포트를 잡으려다 충돌한다. 그래서 **슬롯 번호(0,1,2…)** 를 매겨 포트를 겹치지 않게 분리한다.

**슬롯 배정**: 동시에 띄우는 인스턴스마다 0부터 번호를 준다. 메인 체크아웃이 표준 포트로 떠 있으면 **메인 = 슬롯 0**, 워크트리들은 **슬롯 1, 2…** 로 이어 붙인다.

| 슬롯 N | (예시) api | front | admin |
|---|---|---|---|
| 0 (보통 메인) | `{API_PORT}` | `{FRONT_PORT}` | `{ADMIN_PORT}` |
| 1 | +1 | +1 | +1 |
| N | +N | +N | +N |

> **핵심 — 백엔드는 보통 1개를 공유한다.** 프론트가 여러 개여도 같은 백엔드를 바라보게 하면 config·env 수정이 0이라 제일 깔끔하다. UI 브랜치 여러 개를 한 백엔드로 비교하는 대부분의 경우가 여기 해당한다.
>
> **프록시가 특정 포트에 하드코딩**돼 있으면(예: front dev 서버의 `/api` 프록시가 `127.0.0.1:{API_PORT}` 고정), 백엔드 브랜치를 바꿔 검증할 땐 그 백엔드 워크트리를 **표준 포트(슬롯 0)에 띄우고 메인 백엔드는 끈다.** 그러면 프론트를 안 건드려도 프록시가 바뀐 백엔드를 물게 된다. 포트를 옮기는 게 아니라 "그 자리에 올릴 브랜치를 교체"하는 것.
> 백엔드 브랜치를 2개 이상 동시에 비교해야 할 때만 백엔드 포트까지 슬롯만큼 올리고, 그 프론트의 프록시 타깃도 함께 바꾼다(추적 파일이면 커밋 전 되돌린다). 비용이 있으니 꼭 필요할 때만.

### 5-3. repo별 실행 (슬롯 N의 포트로)

dev 서버는 계속 떠 있어야 하므로 **`run_in_background`로 띄우고**, 로그에서 `ready`/`listening`을 확인한 뒤 **각 워크트리의 접속 URL을 슬롯별로 정리해 사용자에게 안내**한다.

```bash
cd repository/<repo>-worktrees/<티켓번호>
yarn dev --port <슬롯 포트>   # ← run_in_background: true 로 실행
```

- 포트 지정 방식은 프레임워크마다 다르다(Vite `--port`, Next `-p <포트>` 등). 포트를 파일 수정 없이 CLI 인자로 넘길 수 있는지 확인한다.
- **이 repo에 없는 백엔드에 의존하는 기능**은 로컬에서 안 돈다. 어떤 기능이 외부 백엔드에 의존하는지 커스터마이징 주석에 적어두고, 확인 체크리스트에서 그 부분은 "로컬 확인 불가"로 표기한다.

### 5-4. 확인 후 정리

- 변경한 화면/엔드포인트가 의도대로 도는지 확인하고, 결과(혹은 막힌 의존성)를 사용자에게 보고한다.
- 확인이 끝나면 **백그라운드로 띄운 dev 서버를 종료**한다. (워크트리 폴더 자체는 10단계 규칙대로 임의 제거하지 않는다.)
- 병렬로 여러 슬롯을 띄웠다면 슬롯별로 어느 워크트리가 어느 URL인지 한눈에 정리해 보고하고 모두 종료한다.

## 6. 커밋 (워크트리 안에서)

검증이 통과하면 **자동으로** 커밋한다. 사용자에게 따로 물어보지 않는다.
브랜치는 1단계에서 워크트리와 함께 이미 생성됐으니, 워크트리 폴더 안에서 스테이징·커밋만 하면 된다.

```bash
cd repository/<repo>-worktrees/<티켓번호>
git add {수정된 파일들}
git commit -m "<티켓번호> <type>: {요약}"
# 예: git commit -m "PROJ-1712 fix: 센터별 상세 카운트 불일치 수정"
```

- 커밋 메시지 제목은 `<티켓번호> <type>: <요약>` 형식. `type`은 변경 성격(fix/feat/refactor 등)에 맞게.
- 수정한 repo가 여러 개면 각 워크트리에서 **동일 티켓번호 형식**으로 따로 커밋한다.

## 7. push & PR 생성 (워크트리 안에서)

커밋이 끝나면 **자동으로** push하고 PR을 생성한다. 사용자에게 따로 물어보지 않는다.
코드 검토는 PR에서 사용자가 하므로, **PR URL을 클릭 가능한 링크로** 사용자에게 바로 전달한다.

> ⚠️ `gh`는 shell alias/함수에 가려질 수 있으니, alias 문제가 의심되면 절대경로(`command gh` 또는 `$(which -a gh)` 확인)로 실행한다.

```bash
cd repository/<repo>-worktrees/<티켓번호>
git push -u origin <티켓번호>

gh pr create --title "[<티켓번호>] <type>: {요약}" --body "$(cat <<'EOF'
## Summary
- 이슈: https://{JIRA_HOST}/browse/<티켓번호>
- {변경 내용 1~3줄 요약}

## Changes
- {변경된 파일과 수정 내용 목록}

## Test plan
- [ ] {테스트 항목들}

Generated with [Claude Code](https://claude.com/claude-code)
EOF
)"
```

- 수정한 repo가 여러 개면 각 워크트리에서 같은 티켓번호로 push·PR을 각각 올린다.
- **PR과 이슈 URL은 항상 클릭 가능한 링크로 사용자에게 알린다.** 빠뜨리지 말 것.

```
✅ 완료

| 항목 | 링크 |
|------|------|
| PR   | https://github.com/<org>/<repo>/pull/NNN |
| 이슈 | https://{JIRA_HOST}/browse/<티켓번호> |
```

## 8. 로컬 서버 기동 (워크트리 안에서 — 사용자 요청 시에만)

> 🚫 **PR 생성 후 자동으로 서버를 띄우지 않는다.** 매번 자동 기동하면 기존에 떠 있는 서버와 충돌하고, 확인할 필요가 없는 작업에도 서버가 떠버린다.
>
> **7단계(PR 생성)에서 기본 흐름은 끝난다.** 로컬 서버 기동(8단계)·동작 확인(9단계)은 **사용자가 직접 확인하고 싶다는 의사를 명시할 때만** 진행한다.
> - 트리거 예: "서버 켜줘", "로컬에서 띄워줘", "확인해보고 싶어", "동작 확인하자" 등.
> - 7단계 완료 후에는 "로컬에서 직접 확인하시려면 '서버 켜줘'라고 말씀해 주세요" 한 줄만 안내하고 멈춘다.

사용자가 서버 기동을 요청하면, "직접 실행해보세요"라고 안내만 하지 말고 **Claude가 백그라운드(`run_in_background: true`)로 실행**해서 사용자가 바로 브라우저에서 확인할 수 있게 한다.

> ⚠️ **프론트/어드민만 수정한 티켓이라도 의존하는 백엔드(API 서버)를 같이 띄운다.** 프론트는 `/api` 프록시로 백엔드에 의존하므로, API 서버 없이는 로그인조차 안 될 수 있다. 프론트 워크트리만 띄우고 끝내지 말 것.

<!-- SCK:REMOTE-ONLY:START -->
> **🖥️ 원격 서버 환경 — 접속 링크는 내부/외부 2가지를 같이 준다**: 작업 환경이 로컬이 아니라 **원격 서버**라면, `http://localhost:<port>` 하나만 주면 사용자가 접속할 수 없다. 아래 두 줄을 같이 제시한다.
> 1. **내부 IP:port** — `hostname -I`로 매번 확인한 사설 IP(고정 하드코딩 금지, DHCP로 바뀔 수 있음) + 서비스 포트.
> 2. **외부 DDNS:port** — 포트포워딩 규칙에 맞는 외부 호스트:포트. DDNS 호스트명·포트 규칙은 사용자가 알려준 값을 그대로 쓰고 **절대 추측/생성하지 않는다** — 모르면 안내 전에 먼저 물어본다. (포트포워딩이 안 걸려 있으면 외부 링크로 접속이 안 될 수도 있으니 확인을 요청한다.)
>
> 로컬 환경이면 이 블록은 무시하고 `localhost` 링크만 준다.
<!-- SCK:REMOTE-ONLY:END -->

### 8-1. 의존 백엔드(API 서버) 먼저 기동

어느 코드를 올릴지는 아래 기준으로 결정한다:

| 이번 티켓에서 백엔드를 수정했나? | 어디서 띄울 것인가 |
|---|---|
| **아니오** (프론트/어드민만 수정) | 메인 체크아웃: `repository/<api-repo>` |
| **예** (백엔드 워크트리 있음) | 해당 워크트리: `repository/<api-repo>-worktrees/<티켓번호>` |

```bash
# 표준 포트가 이미 사용 중이면 먼저 정리
lsof -ti:{API_PORT} | xargs kill -9 2>/dev/null
cd /절대경로/repository/<api-repo>   # 또는 워크트리 경로
yarn watch   # ← run_in_background: true (기동 방식은 프로젝트에 맞게)
```

기동 후 헬스체크(예: `curl -s -o /dev/null -w "%{http_code}" http://localhost:{API_PORT}/`)로 확인한다.

### 8-2. 프론트/어드민 워크트리 — 포트 자동 결정 (⚠️ 하드코딩 금지)

> ⚠️ **슬롯 포트를 그냥 쓰지 말 것.** 이미 다른 워크트리가 그 포트를 잡고 있으면 해당 프로세스를 죽이고 포트를 빼앗아버린다. **기동 전에 반드시 빈 슬롯을 확인하고 거기에 맞는 포트를 써야 한다.**

```bash
# 표준 포트~+5 중 비어있는 첫 번째 포트를 찾는다
for p in {FRONT_PORT} $(({FRONT_PORT}+1)) $(({FRONT_PORT}+2)) $(({FRONT_PORT}+3)); do
  if ! lsof -i:$p -sTCP:LISTEN &>/dev/null; then PORT=$p; break; fi
done
echo "사용할 포트: $PORT"

cd /절대경로/repository/<front-repo>-worktrees/<티켓번호>
yarn dev --port $PORT   # ← run_in_background: true
```

- `node_modules`·gitignore된 env 는 1단계에서 이미 링크돼 있어야 한다. 빠졌으면 1단계 명령으로 먼저 링크한다(심링크 금지 repo는 install 직접).
- 기동 후 헬스체크로 200 이 오는지 확인한다.

### 8-3. 기동 완료 후 사용자에게 안내

서버가 정상 기동되면 **PR·이슈·로컬 URL을 한 표에** 모아 출력하고, 확인할 화면 경로를 한 줄로 안내한다. (7단계 "완료" 표와 별도로 다시 출력하지 말고 이 표 하나로 통합한다.)

```
✅ 완료

| 항목            | 링크                                          |
|-----------------|-----------------------------------------------|
| PR              | https://github.com/<org>/<repo>/pull/NNN      |
| 이슈            | https://{JIRA_HOST}/browse/<티켓번호>         |
| Front (내부)    | http://{내부 IP}:{탐색된 PORT}                 |
| Front (외부)    | http://{DDNS 호스트}:{외부 포트}               |
| API 서버 (내부) | http://{내부 IP}:{API_PORT}                    |

→ {확인할 화면 경로}에 진입해 확인하세요.
```

- 로컬 서버를 띄우지 않는 경우(API만 수정하고 curl로 검증한 경우 등)에는 Front 행을 빼고 PR + 이슈 + API 행만 출력한다.

## 9. 동작 확인 요청 (사용자 검증 대기)

서버를 띄웠으면(8단계) 거기서 끝내지 말고, **"직접 띄워서 확인해 주세요"라고 사용자에게 명시적으로 확인을 요청**하고 **사용자 피드백을 받을 때까지 다음(정리)으로 넘어가지 않는다.** lint/build와 자가 검토가 통과해도 실제 화면·동작이 기획대로인지는 사람이 눈으로 봐야 안다.

확인 요청은 두루뭉술하게 하지 말고, **무엇을 / 어디서 / 어떤 결과를 기대하는지**를 체크리스트로 제시한다.

```
🔍 동작 확인 부탁드립니다 (<티켓번호>)

접속(내부): http://{내부 IP}:{포트}
접속(외부): http://{DDNS 호스트}:{외부 포트}

확인 항목:
- [ ] {화면 A} 진입 시 목록이 뜨는지
- [ ] {변경한 요소}가 반영됐는지
- [ ] {저장/제출} 후 목록에 반영되는지

확인되면 알려주세요. 이상 있으면 어느 화면에서 어떻게 다른지 알려주시면 바로 고치겠습니다.
```

- **확인 결과 분기**:
  - "문제없다/확인했다" → 서버 종료 여부를 정하고(보통 백그라운드 서버 종료) 작업을 마무리한다. (워크트리 폴더는 10단계 규칙대로 임의 제거하지 않는다.)
  - "이상하다/이렇게 안 나온다" → **2단계(코드 수정)로 돌아가** 고치고, 3(검증)→4(변경요약 + 자가검토)→…→8(재기동)→9(재확인) 흐름을 다시 탄다. 이미 push한 브랜치면 수정분을 같은 브랜치에 추가 커밋·push하면 PR에 자동 반영된다.
- 로컬 의존성 한계로 **로컬에서 확인 불가능한 부분**은 체크리스트에서 빼고 "이 부분은 로컬 확인 불가 — 스테이징/QA에서 검증 필요"라고 명시한다.

## 10. (PR 머지 후 사용자 요청 시) 워크트리 정리

**작업이 끝나도 워크트리를 임의로 제거하지 않는다.** 결과물은 각 워크트리의 브랜치에 남겨둔다.
**PR이 머지되고 사용자가 "정리해줘"라고 하면 그때** 아래 순서대로 정리한다.

> ⚠️ **"정리해줘"는 서버 종료 + 워크트리 폴더 삭제 + 로컬 브랜치 삭제를 항상 셋 다 의미한다.** 하나라도 빠뜨리면 "정리"를 완료한 게 아니다 — 10-1·10-2·10-3을 항상 같이 수행할 것.

### 10-1. 백그라운드 서버 종료

8단계에서 띄운 dev 서버를 모두 종료한다. 포트를 기준으로 정리한다.

```bash
lsof -ti:<사용한 포트> | xargs kill -9 2>/dev/null && echo "<포트> 종료" || echo "<포트> 없음"
```

- 어느 포트를 종료했는지 사용자에게 한 줄로 알린다.

### 10-2. 워크트리 폴더 제거

```bash
cd repository/<repo>
git worktree remove ../<repo>-worktrees/<티켓번호>
```

- 1단계에서 만든 **모든 repo의 워크트리 각각에 대해** 정리한다.
- `git worktree remove`가 "Directory not empty"로 실패하면(node_modules 심볼릭 링크 등 잔재) `rm -rf`로 폴더를 먼저 지운 뒤 `git worktree prune`으로 refs를 정리한다.
  ```bash
  rm -rf /절대경로/repository/<repo>-worktrees/<티켓번호>
  cd repository/<repo> && git worktree prune
  ```
- 머지 안 된 작업 변경이 있으면 강제 삭제하지 말고 사용자에게 확인한다.
- 정리 후 `git worktree list`로 제거됐는지 확인하고 사용자에게 알린다.

### 10-3. 로컬 브랜치 삭제

워크트리 폴더를 지워도 브랜치 자체는 로컬에 그대로 남는다. **PR 머지 후 "정리해줘" 요청에는 로컬 브랜치 삭제도 항상 포함**한다.

```bash
cd repository/<repo> && git branch -d <티켓번호>
```

- `-d`는 머지되지 않은 브랜치는 삭제를 거부하므로 안전하다. PR이 실제로 머지됐는지 먼저 확인한 뒤 실행한다(거부되면 사용자에게 확인, `-D` 강제 삭제는 반드시 사용자 확인 후에만).
- 원격 브랜치(`origin/<티켓번호>`)는 보통 PR 머지 시 자동 삭제된다. 남아 있으면 머지 확인 후 `git push origin --delete <티켓번호>`.
