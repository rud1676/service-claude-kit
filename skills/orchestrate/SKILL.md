# Orchestrate — Ready 드레인 실행기 (뒷단)

READY 보드에 쌓인 티켓을 **하나씩 끝까지** 처리하는 "스펙 주도 자율 실행 루프"의 **뒷단**이다.
앞단(티켓+AC 생성)은 [`acceptance-criteria`](../acceptance-criteria/SKILL.md) 스킬이 맡는다.

> **이 두 스킬은 한 쌍이다(앞단/뒷단).** 고칠 땐 짝을 함께 본다. 이 스킬은 **실행·큐잉·Status 매핑**을 소유하고, acceptance-criteria는 **AC 형식·인테이크**를 소유한다.

## 이 스킬은 "조립(orchestrator)" 스킬이다
원자 스킬(블록)을 규칙대로 엮는다:
- **보드 조회·상태 이동** → 이슈 트래커 스킬(`gh-project` / `jiraticket` / `issue-mgmt`)의 메커니즘.
- **구현(격리 워크트리→검증→커밋→PR)** → [`worktree`](../worktree/SKILL.md) 스킬.
- **변경 서술** → [`explain`](../explain/SKILL.md) 스킬.

## 자율 실행 모델 (이 스킬이 "소유"하는 규칙)

**진입점 = 사람이 호출하는 그 순간(A방식).** 이 스킬은 백그라운드 데몬이 아니다 — 상시 폴링하지 않는다. 상태는 스킬이 아니라 **보드(관제탑)** 에 있어, 호출될 때마다 보드를 다시 읽고 이어서 한다.

- **수동 트리거**: `/orchestrate`("Ready 돌려줘") 호출 시에만 시작.
- **순차**: 한 티켓을 PR까지 끝낸 뒤 다음. 병렬 워크트리 아님(혼자 PR 검토 + 충돌 회피). 나중에 답답하면 병렬 전환.
- **드레인 범위**: READY를 Priority 순으로 **싹 다** 처리 → 다 끝나거나 큐 걸리면 요약 보고.
- **게이트 = 큐잉**: 아래 **3개 트리거**에서만 멈춰 IN REVIEW로 큐잉하고, **멈추지 않고** 다음 티켓 진행.
  1. **권한/인증** 변경
  2. **데이터** (마이그레이션·파괴적·비가역 작업)
  3. **의미갈림** (의도한 동작을 확정할 수 없음 — 해석이 갈리거나 규칙이 어디에도 안 적혀 있음)
- **명백한 버그**(내 새 코드 결함)는 큐 아님 → 자가수정 후 계속. 버그인지 의도인지 애매하면 3번(의미갈림)으로 큐.
- 나머지 자잘한 결정(네이밍·파일 위치·컴포넌트 재사용·스타일 findings)은 **결정하고 계속**, 로그만 남김.

### Status ↔ 루프 매핑 (정본)
| 역할 상태 | 의미 | 옮기는 주체 |
|---|---|---|
| **BACKLOG** | 사용자가 던진 raw 이슈 / AC 초안(미승인) | 사용자·acceptance-criteria |
| **READY** | **AC 승인 완료 = 자율 GO 신호.** 이 스킬은 READY 칸만 집어감 | 사용자(드래그 = 승인 서명) |
| **IN PROGRESS** | worktree에서 작업 중 | 이 스킬 |
| **IN REVIEW** | PR 올림 → 사람 검토 대기 (큐 걸린 것도 여기) | 이 스킬 |
| **DONE** | 검토 통과 + 머지 | 사용자/자동 |

> 실제 트래커의 상태 이름은 프로젝트마다 다르다(GitHub Projects 기본 `Backlog/Ready/In progress/In review/Done`, Jira 예 `To Do/In Progress/In Review/Done`). 아래 커스터마이징 주석에서 역할 상태 → 실제 이름을 매핑한다.

## 단계

### 0. 대상 보드 확정
트래커를 **추측하지 말고 중앙 설정에서 읽는다**(우선순위 순):
- **(a) `CLAUDE.md`의 `service-kit:config` 블록**의 "프로젝트 관리 툴" 값 — install.sh가 적어둔다. `jira`→`jiraticket`, `ghproject`→`gh-project`, `none`→없음. 있으면 그대로 쓴다.
- **(b) config 블록이 없으면** `.claude/skills/`를 스캔(1개→그것, 여러 개→사용자에게 물음).
- 트래커가 `none`/없음이면 "트래커 없음 — 보드 드레인 불가"라 알리고 종료.

### 1. READY 조회
트래커 스킬로 **READY 상태** 티켓을 가져와 **Priority(P0→P1→P2)** 순으로 정렬한다.
READY가 비어 있으면 "처리할 READY 티켓 없음"이라 알리고 종료.

### 2. 순차 드레인 — 각 티켓마다
정렬된 순서로 하나씩:

1. **AC 읽기** — 티켓 본문의 AC(목표/완료조건/안 할 것)를 읽는다. 대상 repo(들)도 확정.
2. **큐 판정** — 이 작업이 큐 트리거(권한/데이터/의미갈림)에 해당하면:
   - 티켓을 **IN REVIEW**로 옮기고, **왜 큐잉했는지 사유를 댓글**로 남긴다. **다음 티켓으로 넘어간다(멈추지 않음).**
3. **구현** — 큐가 아니면 티켓을 **IN PROGRESS**로 옮기고, `Skill` 도구로 **`worktree`** 를 호출한다. 넘기는 값:
   - `<티켓번호>`: 브랜치 식별자(트래커 키 또는 `issue-<번호>-<슬러그>`)
   - `<type>`: 변경 성격(refactor/fix/feat …)
   - 수정 대상 repo: AC의 대상
   - 변경 요지: AC(목표+완료조건+안 할 것)
   - **worktree의 자가검토 게이트는 이 루프에선 큐잉으로 처리**: 버그성 findings는 자가수정, 애매하면 2번처럼 큐.
4. **검증(worktree 안, repo별)** — 리팩토링의 done = **동작 보존**이므로 반드시 독립 신호를 남긴다:
   - **테스트 인프라가 있는 repo**: 관련 테스트/e2e를 실제로 돌려 통과 = 동작 보존 증명.
   - **테스트가 없는 repo**: dev 서버를 띄워 **핵심 경로 스모크**로 "실제로 도는지" 확인.
   - AC의 완료조건을 실제로 충족하는지 확인한다. (repo별 명령은 커스터마이징 주석 참고)
5. **PR & 상태** — worktree가 PR 생성(트래커가 GitHub면 `Closes #N`). 티켓을 **IN REVIEW**로 옮기고 PR 링크를 댓글로.
6. **explain** — `Skill` 도구로 **`explain`**(change 모드) 호출: 이 변경의 구조·데이터 흐름을 서술 + **"실제로 돌려본 결과"를 한 세트로**. (explain은 자백일 뿐이라, 4단계의 독립 검증 신호를 반드시 함께 붙인다.)

### 3. 반복
READY가 빌 때까지 2단계를 반복한다.

### 4. 요약 보고
드레인이 끝나면 한 화면에 정리해 보고한다:
- ✅ **올린 PR** — 티켓/PR 링크 표
- ⏸️ **큐잉된 것** — 티켓 + 큐 사유(권한/데이터/의미갈림 중 무엇)
- 🔎 **검증 결과** — repo별 테스트/스모크 통과 여부
- 🧠 **explain 요약** — 무엇을 어떻게 바꿨는지 핵심

## 하지 말 것
- 상시 자동 실행/폴링(수동 트리거만).
- 큐 트리거 3개 외의 지점에서 멈춰 사용자를 기다리기(자잘한 건 결정하고 계속).
- 병렬 워크트리로 동시 진행(순차 유지 — 나중에 명시적으로 바꾸기 전까지).
- 메인 체크아웃에 직접 수정(모든 수정은 worktree 안).
