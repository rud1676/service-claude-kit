# 브라우저 E2E 확인 → 캡처 결과 문서

> 출발점: 프론트 변경(대시보드 단계별 로딩)을 로컬 → 개발서버 순으로 확인하며 캡처 md 를 만들었더니, 리뷰어가 PR·배포 판단을 문서만 보고 할 수 있었다. 그 절차와 밟은 함정을 묶었다.
> **골드 샘플**: 이 형식으로 잘 쓴 결과 문서가 생기면 맨 아래 `프로젝트 커스터마이징`에 경로를 적어 둔다. 형식이 애매하면 그 문서를 Read 해서 따라 한다.

> **이 스킬은 "고쳐 쓰는 참고 구현"이다.** 절차(측정·캡처 분리 → 캡처 직접 확인 → 기대/결과 문서)와 함정 대응은 스택과 무관하게 보편이다. **URL·로그인 방식·로컬 기동법·문서 위치**는 프로젝트마다 다르다 — 맨 아래 `프로젝트 커스터마이징` 주석을 채운다.

이 스킬의 산출물은 **"사람이 PR·배포를 판단할 수 있는 근거 문서"** 다. 테스트 코드를 레포에 남기는 게 아니다. 실행 스크립트는 레포 밖(`/tmp/e2e-<slug>/`)에 둔다.

| [`scenario-test`](../scenario-test/SKILL.md) 와의 차이 | scenario-test | browser-e2e |
|---|---|---|
| 무엇을 | 여러 API 를 순서대로 부르는 **테스트 코드** | 실제 **브라우저 화면**의 동작 |
| 남는 것 | 레포의 테스트 파일 | 캡처 + 시간표 + 기대/결과 **문서** |
| 언제 | 비즈니스 플로우 회귀 방지 | 화면·로딩·순서 같은 눈으로 봐야 하는 변경의 PR·배포 판단 |

## 0. 시작 전에 정할 것 (모르면 묻는다)

| 항목 | 기본값 | 비고 |
|---|---|---|
| 무엇을 확인하나 | 요청에서 "기대 동작" 목록으로 뽑는다 | §4 확인 결과 표의 행이 된다. 3~7개 |
| 어디서 | 머지 전 = **로컬**, 머지 후 = **개발서버** | 운영(live)은 사용자가 명시할 때만, 읽기만(1-C) |
| 어느 화면·조건 | URL·필터 값 확정 | 재현 가능하게 쿼리스트링까지 고정 |
| 캡처 대상 | 상태가 바뀌는 순간마다(로딩 → 단계 → 완료 → 조건 변경) | |
| 문서 위치 | `docs/YYYY-MM-DD-<티켓>-<slug>-test.md` + `docs/assets/YYYY-MM-DD-<티켓>-<slug>[-dev]/` | 환경만 바꿔 다시 하면 **같은 문서를 갱신**하고 이전 환경 결과는 `<details>` 로 접는다 |

## 1. 환경 준비

### 1-A. 로컬 (머지 전)

- 프로젝트의 로컬 기동법대로 띄운다(커스터마이징 값). **이미 떠 있는 서버는 그대로 쓰고**, 어느 체크아웃·버전인지 확인해 문서에 적는다(`ss -ltnp`, `readlink /proc/<pid>/cwd`)
- 로그인이 외부 인증 서버 등에 막혀 로컬에서 안 되면 **목업 로그인**: 토큰을 직접 서명해 쿠키/localStorage 에 넣고, 인증 서버 호출만 `page.route` 로 가짜 응답
- dev 서버(예: next dev) 첫 진입은 컴파일로 수십 초 걸린다 → **워밍 1회** 후 측정

### 1-B. 개발서버 (머지 후)

- **배포 완료부터 확인**: CI 배포 run 이 진행 중이면 `gh run watch <id> --exit-status` 를 **백그라운드**로 걸고 기다린다(짧은 폴링 금지). 머지 커밋이 배포 대상인지 확인
- 계정 비밀번호는 **환경변수(`U`·`P` 등)로만** 넘긴다 — 스크립트·문서에 쓰지 않는다. 모르면 사용자에게 묻는다

### 1-C. 운영 (사용자가 명시할 때만)

- 조회 화면만. 무거운 API 를 반복·동시 호출하지 않는다 — 측정 1회, 동시 실험은 승인 후
- 쓰기 동작(등록·삭제·저장)은 하지 않는다

## 2. 실행 — 두 번 돌린다 ★

**시간 측정과 캡처는 따로 돌린다.** 캡처를 위해 응답을 늦추거나 붙잡으면 시간이 왜곡된다.

| 실행 | 목적 | 개입 | 문서 위치 |
|---|---|---|---|
| ① 측정 | 요청 시작·끝·동시 개수 | **없음** | §2 시간표 |
| ② 캡처 | 상태별 화면 | 필요할 때만 아래 둘 중 하나 | §1 캡처 |

캡처 개입 고르기:

| 상황 | 쓰는 것 | 문서에 적을 말 |
|---|---|---|
| 응답이 너무 빨라 로딩 상태가 안 찍힌다(로컬·작은 dev 데이터) | `holdGate` — 요청을 붙잡고 한 묶음이 다 나가면 찍은 뒤 풀기 | "캡처의 '불러오는 중'은 찍으려고 붙잡은 상태. 붙잡은 동안 다음 요청이 안 나간 것 자체가 순서 동작의 근거" |
| 상태가 시간 흐름으로만 바뀐다 | `delayResponses` — 전 요청 N초 지연 | "인위 지연 N초 — 시간표는 실제 속도가 아님" |
| 충분히 느리다 | 개입 없음, 상태 문구를 폴링하며 바뀔 때 찍기 | — |

헬퍼: [`scripts/e2e-kit.cjs`](scripts/e2e-kit.cjs) — `open` · `formLogin` · `trackRequests` · `holdGate` · `delayResponses` · `snap`.

```js
// /tmp/e2e-<slug>/run.cjs   실행: PLAYWRIGHT=<레포>/node_modules/playwright U=… P=… node run.cjs
const kit = require('<설치 경로>/.claude/skills/browser-e2e/scripts/e2e-kit.cjs');
(async () => {
  const { browser, page } = await kit.open();                       // 모바일이면 { viewport: { width: 430, height: 900 } }
  await kit.formLogin(page, { url: BASE + '/login', idSelector: 'input[name="email"]',
    id: process.env.U, pw: process.env.P, successUrlPart: '/api/me' });  // 로그인 성공 신호 응답
  const net = kit.trackRequests(page, (u) => u.includes('/api/'));
  await page.goto(URL, { waitUntil: 'domcontentloaded' }); net.reset();
  // … 상태 확인 · 조건 변경 시 net.mark('필터 변경')
  await page.waitForTimeout(10000); net.print(); await browser.close();
})();
```

**밟은 함정**

- 로그인: 하이드레이션 전 `fill` → 입력 유실. 로그인 직후 `goto` → 클라이언트 리다이렉트와 경합해 다른 페이지로 끌려감. `formLogin` 이 둘 다 막는다(URL 이 아니라 **성공 신호 응답**을 기다림)
- 상태 문구를 렌더 전에 찾으면 0개라 "끝"으로 오판한다 → 그 문구가 **나타날 때까지** 먼저 기다리고, 판정은 `page.evaluate` 로 DOM 텍스트를 직접 읽는다
- 빠른 서버에서 "상태가 바뀌면 찍기" 폴링은 전체 페이지 캡처(수백 ms)가 못 따라가 단계를 건너뛴다 → `holdGate`
- `pkill -f <패턴>` 은 그 패턴이 든 자기 셸까지 죽인다 → 띄운 서버는 **PID 로** 내린다

## 3. 캡처 확인 (건너뛰지 않는다)

- 찍은 png 를 **Read 로 직접 열어** 기대한 상태(로딩 문구·단계 표시·데이터)가 보이는지 확인한다. 파일명만 보고 문서에 넣지 않는다
- 기대와 다르면(빈 화면·로그인 화면·에러) 원인부터 고치고 다시 찍는다

## 4. 결과 문서 골격

```markdown
# [테스트] <무엇> (<티켓>) — <로컬|개발서버>

> **한 줄 요약** — 어디서 무엇을 확인했고 결과가 어땠나(핵심 숫자 1~2개).

| 항목 | 값 |   ← 이슈·PR 링크 / 코드(브랜치·SHA) 또는 배포 SHA / 환경 / 일시 / 결과 ✅❌

## 0. 테스트 환경·방법     구성 표 + 개입(지연·붙잡기)을 했다면 > [!NOTE] 로 명시
## 1. 단계별 화면          <table> 3열로 캡처 나란히, 각 칸 아래 "여기서 보이는 것" 한 줄 + 단계↔요청 표
## 2. 요청 시간표          mermaid gantt(dateFormat x, 기간은 `NNNms`) + 표(시작·끝·걸린 시간·가장 늦은 요청) + 핵심 관찰 불릿
## 3. 추가 시나리오        조건 변경·재시도 등 — 캡처 1장 + 시각 표
## 4. 확인 결과            | 확인 항목 | 기대 | 결과 |  (✅/❌)
## 5. 이 테스트로 알 수 없는 것   | 항목 | 이유 · 확인 방법 |  (데이터 규모·인위 개입·동시 사용자 등)
<details> 이전 환경 결과(있으면) · 재현 스크립트 위치(레포 밖 경로, 계정은 환경변수) </details>
```

- 이미지 경로는 문서 기준 상대 경로(`assets/<폴더>/NN-설명.png`)
- 시간은 실측값 그대로. 인위 개입한 실행의 숫자를 "속도"로 쓰지 않는다
- ❌ 가 있으면 숨기지 않고 맨 위 요약에 쓴다

## 5. 마무리

- [ ] 띄운 서버를 PID 로 내렸다 — 원래 떠 있던 서버는 건드리지 않았다
- [ ] 문서·스크립트·캡처에 비밀번호·토큰이 없다
- [ ] 캡처를 전부 열어 봤다
- [ ] 결과가 맥락 문서(wiki 등)의 상태를 바꾸면(예: "dev 배포·검증 완료") 그 줄을 갱신하고 테스트 문서를 링크했다
- 사용자에게: 문서 링크 + 확인 결과 표 요약 + "이 테스트로 알 수 없는 것" 한두 줄
