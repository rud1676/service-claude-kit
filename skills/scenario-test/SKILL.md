# 시나리오 테스트 작성 스킬

여러 API를 순서대로 호출하며 **실제 유저 플로우**를 검증한다.
단위 테스트가 API 1개를 다양한 입력으로 본다면, 시나리오 테스트는 API 여러 개를 조합해 비즈니스 흐름이 올바른지 본다.

> **이 스킬은 "고쳐 쓰는 참고 구현"이다.** 절차·규율(플로우 파악 → 설계 확인 → 작성 → 진단 → 브리핑 → 문답)과 원칙("사전 데이터는 API로 만든다", 데이터 격리, 날짜/스케줄러 재현)은 스택과 무관하게 보편이다. **테스트 러너·앱 진입점·DB/ORM·인증 헬퍼·파일 위치**는 프로젝트마다 다르다 — 맨 아래 `프로젝트 커스터마이징` 주석과 [`references/conventions.md`](./references/conventions.md)를 자기 스택에 맞게 채운다. 단위 테스트는 [`unit-test`](../unit-test/SKILL.md) 스킬.

## 단위 테스트와의 차이

| 구분 | 단위 테스트 | 시나리오 테스트 |
|------|-----------|--------------|
| 범위 | API 1개 | API 여러 개 (순서대로) |
| 상태 | 테스트마다 독립 | 이전 스텝의 결과가 다음 스텝의 입력 |
| 데이터 격리 | TEST_PREFIX + 자기 데이터만 삭제 | 동일 |
| 날짜 | 단일 시점 | 여러 시점 (날짜를 바꿔가며) |
| 액터 | 보통 1명 | 여러 명 (유저 + 어드민 + 다른 유저) |
| 검증 | 응답 구조 + DB 상태 | 플로우 전체의 비즈니스 정합성 |

## 사용법

```
/scenario-test
```

인자 없이 실행하면 시나리오 입력을 대기한다.

## 실행 순서

### 0단계: 시나리오 입력 받기

`$ARGUMENTS`가 비어있으면 아래를 출력하고 **개발자의 입력을 기다린다**:

```
시나리오 테스트를 작성합니다. 테스트할 시나리오를 설명해 주세요.

입력 예시:
- 자연어: "사용자가 챌린지에 참여하고 매일 습관을 완료하는 시나리오"
- API 나열: "POST /api/orders/:id/join → POST /api/orders/complete → GET /api/orders/:id/summary"
- 혼합: "로그인 → 참여 → 완료 7일 반복 → 결과 확인"
```

개발자가 시나리오를 입력하면 1단계부터 진행한다.

### 1단계: 시나리오 파악 및 관련 API 병렬 분석

시나리오에 포함된 API를 식별한 후, **Agent 도구로 2~4개의 에이전트를 동시에 띄워** 각 API 그룹을 병렬 분석한다.

#### 1-1. API 식별
시나리오 설명에서 관련 엔드포인트를 모두 식별하고, 라우팅 정의를 검색해 실제 경로와 핸들러 매핑을 확인한다.

#### 1-2. 에이전트 분배 및 병렬 분석
식별된 API들을 도메인 또는 역할 기준으로 그룹핑하고, **그룹당 1개 에이전트**를 할당한다. 모든 에이전트는 **하나의 메시지에서 동시에 호출**해 병렬 실행한다.

**분배 기준**:
- **도메인 기준**: 서로 다른 도메인이면 도메인별로 (예: 주문 에이전트 + 정산 에이전트)
- **역할 기준**: 같은 도메인이라도 어드민 vs 유저 API로 (예: 어드민 생성 에이전트 + 유저 참여 에이전트)
- **최소 2개 / 최대 4개**: API가 2개뿐이어도 각각 1개씩, 많으면 관련성 높은 것끼리 4그룹 이내로

**각 에이전트가 분석할 내용**:
- 라우팅에서 해당 URL의 핸들러 함수와 미들웨어(인증 방식) 확인
- 핸들러를 읽고: 입력 파라미터 / 사전 조건(어떤 데이터가 DB에 있어야 하는지) / 부수 효과(무엇을 생성·수정) / 다음 스텝에 넘길 출력(응답에서 추출할 값)
- 관련 모델/스키마를 읽어 테이블명·컬럼명·연관관계 확인
- 스케줄러/배치 의존 로직이 있는지 확인

#### 1-3. 분석 결과 종합
모든 에이전트 결과를 받아:
1. API 간 **데이터 의존 관계** 정리 (어떤 API 출력이 다음 API 입력인지)
2. **필요한 사전 데이터** 목록 통합
3. **스케줄러/배치 의존 지점** 식별
4. 기존 시나리오 테스트를 참고해 유사 패턴 확인

### 2단계: 시나리오 설계 — 개발자 확인

시나리오 타입을 판별하고, 아래 형식으로 개발자에게 **먼저 보여주고 피드백을 받는다**:

```
## 시나리오 설계: {시나리오 이름}

### 시나리오 타입
- [ ] A. 라이프사이클/CRUD (생성 → 조회 → 수정 → 삭제)
- [ ] B. 유저 저니 (복잡한 비즈니스 로직, 날짜 의존, 다중 액터)
- [ ] C. 인증/권한 플로우
- [ ] D. 혼합

### 액터
| 액터 | 유형 | 역할 |
|------|------|------|
| 유저A | 일반 유저 | 참가자 |
| 어드민 | 시스템 어드민 | 생성/관리 |

### API 플로우
| 순서 | 액터 | API | 목적 | 이전 스텝에서 받는 값 |
|------|------|-----|------|-------------------|
| 1 | 어드민 | POST /api/... | 리소스 생성 | - |
| 2 | 유저A | POST /api/.../join | 참여 | resourceId from #1 |

### 워크플로우 분리
시나리오가 복잡하면 독립 검증 가능한 워크플로우로 분리한다:

| WF | 이름 | 포함 스텝 | 검증 포인트 |
|----|------|----------|-----------|
| WF-01 | 기본 플로우 | #1~#5 | 정상 동작 |
| WF-02 | 엣지 케이스 | #1~#3, #6 | 비정상 입력 처리 |

### 날짜 의존성
- {날짜를 변경해야 하는 스텝과 이유 / 사용할 날짜 범위}

### 스케줄러 의존성
- {스케줄러 실행이 필요한 스텝과 대체 방법}

### 질문
- {비즈니스 로직에서 확인이 필요한 부분}
```

### 3단계: 테스트 코드 작성

[`references/conventions.md`](./references/conventions.md)의 패턴을 **정확히** 따른다.

**파일 위치**: 프로젝트의 시나리오 테스트 배치 규칙을 따른다 (예: `test/scenarios/{도메인}/{시나리오명}.spec.js`). 도메인 디렉토리가 없으면 생성. (규칙은 커스터마이징 블록)

**코드 구조** (개념 — 스택 무관):

```
// 1. Helper 함수 (API 래퍼) — 실패 시 throw
// 2. 최상위 describe/그룹 — 공용 데이터 + 생성 ID 추적(createdIds)
//    setup: 어드민·공용 리소스 생성 (API로)
//    teardown: 자기가 만든 데이터만 FK 역순 삭제
// 3. 워크플로우별 nested 그룹 (WF-01, WF-02 …) — 각자 독립 데이터
// 4. 순서가 중요한 스텝 테스트들 (이전 스텝 결과를 다음 스텝이 사용)
```

**핵심 규칙** (스택과 무관한 보편 규율):

1. **사전 데이터는 API 호출로 생성 — DB 직접 INSERT 금지**: 시나리오 테스트의 목적은 "실제 유저가 앱을 쓰는 흐름"의 재현이다. INSERT로 DB를 직접 조작하면 실제 비즈니스 로직(validation·부수 효과·훅·트랜잭션)이 건너뛰어져 "실서비스에선 절대 만들어질 수 없는 상태"를 테스트하게 된다. **리소스를 만드는 API가 존재하면 반드시 그 API를 호출해 만든다.** INSERT는 **해당 리소스를 만드는 API가 아예 없을 때**만 허용(내부 참조 테이블, 국가/법인 같은 시스템 메타).
2. **Helper 함수는 실패 시 throw**: 헬퍼 내에서 성공 상태가 아니면 에러 메시지와 함께 throw. 중간 스텝 실패를 빠르게 감지.
3. **TEST_PREFIX로 데이터 격리**: 파일명 기반 접두사로 유니크 데이터 생성. 전체 삭제(TRUNCATE 등) 금지.
4. **createdIds로 ID 추적**: setup/스텝에서 생성한 모든 리소스 ID를 추적하고, teardown에서 자기 데이터만 삭제.
5. **삭제 순서는 FK 역순**: 자식(FK 있는) 먼저, 부모 나중.
6. **워크플로우 간 데이터 격리**: 각 WF 그룹의 setup에서 자기 WF 데이터만 생성.
7. **날짜 조작은 날짜 고정 유틸로**: 날짜 의존 스텝은 반드시 래핑.
8. **스케줄러 의존 로직은 flush 함수로**: 스케줄러가 필요하면 그 핵심 로직을 직접 호출하는 flush 함수를 정의(기다리기로 해결 금지).
9. **스텝 순서 의존 OK**: 시나리오에서는 같은 그룹 내 스텝 순서가 의미 있다.

**절대 하지 않을 것**:
- **사전 데이터를 DB에 INSERT로 직접 만들지 않는다** — 만드는 API가 있으면 반드시 그 API 호출. API가 없는 경우(시스템 메타)만 예외.
- 테이블 전체 비우기(TRUNCATE 등) 금지 — 다른 테스트 데이터를 날린다
- 존재하지 않는 API 경로·파라미터를 추측하지 않는다 — 라우팅에서 확인
- 스케줄러 동작을 "기다리기"로 해결하지 않는다 — flush 함수로 직접 실행
- 단위 테스트에서 이미 검증한 에러 케이스(필드 누락, 401 등)를 시나리오에서 반복하지 않는다

### 4단계: 테스트 실행 및 검증

이 프로젝트의 **테스트 실행 명령**으로 해당 시나리오 파일을 돌린다 (명령은 커스터마이징 블록).

#### 실패 시 진단 프로세스

**A. 코드 버그인 경우** (직접 수정 가능):
1. 에러 메시지로 **어느 스텝**에서 실패했는지 확인
2. 해당 스텝의 핸들러를 다시 확인
3. 이전 스텝이 생성한 데이터가 올바른지 DB 조회로 검증
4. 수정 후 재실행

**B. 시나리오 누락인 경우** (개발자 확인 필요):
사전 조건이 충족되지 않아 실패하면 **빠진 선행 스텝**이 있을 수 있다. 반드시 개발자에게 확인받는다.

```
## 시나리오 누락 확인

### 실패한 스텝
- 스텝 2: POST /api/.../join → 400 (사전 조건 미충족)

### 원인 분석
{핸들러 분석 결과, 어떤 선행 데이터/스텝이 빠졌는지}

### 추가가 필요한 선행 스텝 (추정)
| 순서 | API | 목적 |
|------|-----|------|
| 0-1 | POST /api/... | ... |

### 질문
1. 위 선행 스텝을 시나리오에 추가해도 될까요?
2. 다른 방법으로 사전 데이터를 세팅해야 하나요?
```

답변을 받은 후: 설계(2단계) 업데이트 → 코드 수정 → **재실행**. 통과할 때까지 반복.

### 5단계: 개발자 브리핑 (필수)

작성이 끝나면 **반드시** 아래 형식으로 설명한다.

```
## 시나리오 테스트 브리핑: {시나리오명}

### 이 시나리오가 검증하는 것
- {비즈니스 플로우 1~2문장}
- 관련 도메인 / 관련 API

### 액터 구성
- {각 액터의 역할과 권한}

### 워크플로우별 요약
| WF | 이름 | 검증 포인트 | 이 테스트가 없으면 놓치는 것 |
|----|------|-----------|------------------------|

### Helper 함수 가이드
| 함수명 | 하는 일 | 호출 API | 반환값 |
|--------|--------|---------|--------|

### 데이터 플로우 다이어그램
스텝1 (어드민: 생성)
  └─ resourceId
       ├─ 스텝2 (유저: 참여)
       └─ 스텝3 (유저: 완료)
            └─ 스텝4 (검증)

### 시나리오 테스트가 커버하지 않는 것
- {단위 테스트로 커버할 부분 / 수동 테스트 필요 / 추가 시나리오 필요}

### 개발자 확인 체크리스트
- [ ] API 호출 순서가 실제 유저 플로우와 일치하는가?
- [ ] 각 스텝 사이에 빠진 API 호출이 없는가? (예: 스케줄러가 해야 할 작업)
- [ ] 날짜 설정이 비즈니스 규칙에 맞는가?
- [ ] 워크플로우가 실서비스 주요 케이스를 충분히 커버하는가?
- [ ] 추가할 엣지 케이스 워크플로우가 있는가?
```

### 6단계: 개발자 문답 (필수)

브리핑 후, 개발자의 이해도를 확인하고 AI가 놓친 부분을 찾는 문답을 진행한다. (개발자를 루프 안에 남겨두는 핵심 단계)

#### 파트 A: 사전 데이터 구성 이해 (2문제)

- **Q1. 사전 데이터 생성 과정** — 테스트 시작 전에 어떤 데이터를 어떤 방법(API 호출/DB INSERT)으로 만들었고 왜 필요한지
- **Q2. 데이터 의존 관계** — 사전 데이터 간 연결과 스텝 간 전달되는 값

**⚠️ 질문 설계 시 금지 사항**

답이 **"격리성 보장"**, **"전체 삭제 금지"**, **"다른 테스트에 영향 안 주려고"**, **"데이터 정리"**, **"FK 역순"** 같은
일반론으로 귀결되는 질문은 하지 않는다. 컨벤션에 이미 있는 뻔한 답이다.

대신 **이 시나리오에만 고유한 설계 결정**을 묻는다:
- ❌ "teardown에서 왜 이 순서로 삭제하나요?" → "FK 때문에" (뻔함)
- ✅ "이 시나리오에서 참조 리소스를 최상위 setup에서 만들어 WF끼리 공유하는 이유는? 각 WF마다 새로 만들면 안 되나요?"
- ✅ "WF-03에서 유저를 3명 만든 이유는? 2명으로는 어떤 검증이 불가능해지나요?"
- ✅ "유저C를 다른 그룹/상태로 시작시킨 선택이 어떤 검증을 가능하게 했나요?"

문답은 개발자가 **본인 시나리오의 의도**를 설명할 수 있는지 확인하는 자리이지 컨벤션 암기 테스트가 아니다.

#### 파트 B: AI가 놓친 시나리오 찾기 (2문제)

- **Q3. 빠진 워크플로우** — 현재 테스트가 커버 못 하는 실서비스 시나리오가 있는지 (힌트 제공)
- **Q4. 동시성/정합성** — 여러 유저가 동시에 같은 리소스에 접근하거나 예상치 못한 순서로 호출하는 경우

#### 마무리
4문제가 끝나면:
1. **"이 시나리오 테스트가 보호하는 핵심 비즈니스 플로우를 한 문장으로?"** 으로 마무리
