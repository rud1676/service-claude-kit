# Acceptance Criteria — 작업 인테이크 & AC 확정 (앞단)

추상적인 작업 요구를, 자율 실행이 가능한 **작은 티켓 + AC**로 바꿔 이슈 트래커에 올리는 스킬이다.
"스펙 주도 자율 실행 루프"의 **앞단**이고, 뒷단(Ready 드레인 → 구현 → 검증)은 [`orchestrate`](../orchestrate/SKILL.md) 스킬이 맡는다.

> **이 두 스킬은 한 쌍이다(앞단/뒷단).** Status 매핑·큐 트리거 같은 공유 개념은 각 스킬이 자기 몫을 "소유"하고 상대를 참조한다. 고칠 땐 짝을 함께 본다. (이 스킬은 **AC 형식·인테이크**를 소유, orchestrate는 **실행·큐잉**을 소유)

## 이 스킬은 "조립(orchestrator)" 스킬이다
직접 다 하지 않고 **원자 스킬(블록)을 조립**한다:
- **인터뷰** → [`grill-me`](../grill-me/SKILL.md) 스킬을 **`Skill` 도구로 호출**(한 번에 한 질문·추천 곁들임·스레드 끝까지). grill-me가 설치돼 있지 않으면, 아래 "grill-me 규율"을 인라인으로 직접 따른다.
- **이슈 생성** → 이 프로젝트에 설치된 이슈 트래커 스킬(`gh-project` / `jiraticket` / `issue-mgmt` …)에 위임.

## 역할 분담 (이 루프의 핵심 계약)
- **사용자 = 방향·원칙(what/왜).** "어떤 구조가 좋은가" 같은 아키텍처 판단은 사용자 몫.
- **Claude = 현재 코드 점검 + 분해 제안(how 후보).** 방향 없이 "그냥 정리해줘"만 오면 그건 **의미갈림** → grill로 방향부터 끌어낸다(추측으로 지어내지 않는다).

---

## 단계

### 1. 큰 맥락 — 작업 종류 확정
가장 먼저, 이번 작업이 어느 종류인지 하나로 확정한다(종류마다 이후 질문과 AC 모양이 갈린다). 사용자에게 묻는다:

> 이번 작업은 어느 쪽인가요?
> 1) 리팩토링 (구조 개선)  2) 코드 리뷰  3) 테스트 커버리지 목표 달성
> 4) 새 기능 추가  5) 대규모 필드명/식별자 변경(사용처 많음)  6) 성능 최적화  7) 기타

### 2. grill-me 호출 — 추상 → 구체
`Skill` 도구로 **`grill-me`** 를 호출해, 고른 작업 종류 + 사용자의 초기 서술을 subject로 인터뷰한다.
**목표**: "티켓 + AC를 적당한 높이(what까지)로 쓸 수 있을 만큼" 구체화될 때까지.

> **grill-me 규율(설치 안 됐을 때 인라인용)**: 한 번에 질문 하나 · 각 질문에 추천안 곁들임 · 한 갈래를 끝까지 판 뒤 다음 갈래 · 코드로 답할 수 있는 건 물어보지 말고 직접 Grep/Glob/Read로 확인 · 약한 근거엔 되물어 압박.

종류별로 파고들 축(grill-me가 따라갈 스레드 힌트):
| 종류 | 끝까지 물어야 할 것 |
|---|---|
| 리팩토링 | 목표 구조(무엇을 어떤 모양으로), 동작 보존 기준, 범위 경계 |
| 코드 리뷰 | 리뷰 대상 범위, 판정 기준(무엇을 문제로 볼지) |
| 테스트 커버리지 | 대상 범위(어느 라우터/모듈), 커버리지 기준(예: 라우터마다 최소 1개) |
| 새 기능 | 기능의 관찰 가능한 동작, 입력/출력, 범위 밖 |
| 필드명 변경 | 대상 식별자, 모든 사용처, 하위호환/마이그레이션 필요 여부 |
| 성능 최적화 | 병목 지점, 목표 수치(before→after), 측정 방법 |

- grill 도중 코드로 답할 수 있는 건 **직접 점검(Grep/Glob/Read)** 해서 근거를 댄다.
- 인터뷰가 수렴(모든 갈래 해소)되면 그 결과를 갖고 3단계로.

### 3. AC 확정 (형식 + 높이) — 이 스킬이 "소유"하는 규칙
각 티켓의 AC를 아래 규칙으로 쓴다.

- **형식(고정 3칸)**: `목표(변경 딱 하나)` / `완료조건` / `안 할 것(범위 상한)`.
- **높이(altitude) = what까지만.** 무엇을 원하는지가 애매하지 않을 만큼만 쓰고, **how(파일·함수·구현 방식)는 실행 스킬에 맡긴다.**
  - 너무 높으면(예: "코드 좀 정리해줘") → 의미갈림 → 큐 → 사용자 대기.
  - 너무 낮으면(줄 단위 diff까지 지정) → 사용자가 사실상 코딩한 것 → 위임 이득 0.
- **완료조건 칸은 종류별로 모양이 다름**:
  - **리팩토링 → 동작 보존.** 위험도로 나눔: (A) 로직을 실제로 재구성 → **characterization test(현재 동작 고정 테스트) 먼저**; (B) 순수 이동/추출(시그니처 동일) → 스모크/스냅샷으로 충분. 테스트 없는 곳은 **사용자가 스모크 시나리오 한 줄**을 준다.
  - **새 기능 → 관찰 가능한 AC**("이 입력 → 이 결과").
  - **테스트 커버리지 → 대상 범위 + 커버리지 기준**(예: 라우터마다 최소 1개).
  - **필드명 변경 → 모든 사용처 갱신 + 동작 보존.**
  - **성능 → 목표 지표(before→after) + 측정 방법.**

### 4. 계획서 산출 — `plan/{테마}-make-ticket.md`
아래 틀로 계획서를 쓴다(사용자가 한눈에 검토 가능하도록). `plan/`은 워크스페이스의 임시 작업 폴더다(완료 후 삭제 가능).

```
# {테마} — 티켓 계획 (작업 종류: {종류})

## 방향 / 원칙
(사용자가 준 방향 + grill로 확정된 것)

## 부모(테마) 티켓
- 제목 / 한 줄 목표

## 자식 티켓들 (작은 단위)
### #1 {제목}
- 목표: (변경 딱 하나)
- 완료조건: (종류별 형식)
- 안 할 것:
- 대상 repo / 순서·의존:
### #2 ...

## 순서 / 의존 그래프
(무엇이 무엇보다 먼저인지)
```

### 5. 이슈 자동 생성 (트래커 확정)
계획서를 사용자에게 보여준 뒤 티켓을 만든다.
1. **트래커 확정** — 추측하지 말고 **중앙 설정에서 읽는다**(우선순위 순):
   - **(a) `CLAUDE.md`의 `service-kit:config` 블록** — install.sh가 설치 시 여기에 "프로젝트 관리 툴"을 적어둔다. `jira`→`jiraticket`, `ghproject`→`gh-project`, `none`→트래커 없음. **이게 있으면 이 값을 그대로 쓴다**(폴더 스캔·되묻기 없음).
   - **(b) config 블록이 없으면**(예: skills.sh로 낱개 설치돼 CLAUDE.md가 없는 경우) `.claude/skills/`를 스캔한다 — 트래커 스킬 1개면 그것, 여러 개면 사용자에게 한 번 물음.
   - **트래커가 `none`/0개** → 이슈 생성은 건너뛰고 계획서(md)만 남긴다.
2. **부모 tracking 이슈 1개 + 자식 sub-issue N개** 생성. **AC를 이슈 본문에** 넣고(댓글 아님 — 본문이 유일한 진실), 상태는 **BACKLOG(초안, 미승인)**.
3. 생성된 이슈 링크를 사용자에게 표로 보고하고, 계획서 파일 경로도 안내한다.

> 이렇게 BACKLOG에 올라간 티켓을, 사용자가 **READY로 옮기면(= AC 승인 서명)** [`orchestrate`](../orchestrate/SKILL.md)(또는 "Ready 돌려줘")가 그때부터 자율 드레인한다. Status 이름·의미의 정본은 orchestrate 스킬에 있다.

## 하지 말 것
- 방향(아키텍처 목표)을 사용자 대신 지어내기 — 그건 의미갈림. grill로 끌어낸다.
- AC를 너무 낮은 높이로(파일·줄 단위 diff까지) 쓰기 — 그건 실행 스킬 몫.
- 이 단계에서 코드 수정 — 여긴 인테이크·계획까지다. 구현은 `orchestrate`→`worktree`.
