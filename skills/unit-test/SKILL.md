# API 단위 테스트 작성 스킬

실제 앱/라우터 진입점을 HTTP 클라이언트로 호출해 **엔드포인트 1개**를 테스트한다.
DB는 mock하지 않고 **실제 테스트 DB**를 쓴다(외부 서비스만 mock). API 1개에 대해 다양한 입력·상태·에러를 검증한다.

> **이 스킬은 "고쳐 쓰는 참고 구현"이다.** 절차·규율(무엇을 어떤 순서로, 무엇을 테스트하고 무엇을 안 하는가, 브리핑·문답)은 스택과 무관하게 보편이다. 반면 **테스트 러너 명령·앱 진입점 import·DB/ORM·인증 토큰 생성·파일 위치 규칙**은 프로젝트마다 다르다 — 맨 아래 `프로젝트 커스터마이징` 주석대로 자기 스택에 맞게 채운다. 상세 코드 패턴은 [`references/conventions.md`](./references/conventions.md).

## 사용법

```
/unit-test GET /api/orders/:id/items
/unit-test POST /api/orders
/unit-test POST /api/admin/products
```

- `{HTTP 메서드} {URL}` 형태로 입력
- URL은 라우터에 정의된 경로 그대로 사용 (`:param` 포함)

## 실행 순서

### 1단계: 엔드포인트 분석

1. `$ARGUMENTS`에서 HTTP 메서드와 URL을 파싱
2. **라우터/라우팅 정의**를 검색해 해당 URL에 매핑된 핸들러 함수와 미들웨어(인증 방식) 확인
3. **핸들러 함수**를 읽고:
   - 어떤 요청 필드를 쓰는지 (body, path/query param, 업로드 파일, 인증 주체)
   - 어떤 모델(테이블)을 조회/생성/수정하는지
   - 어떤 에러를 던지는지 (이 프로젝트의 에러 정의 참고 — 커스터마이징 블록)
   - 트랜잭션 사용 여부
   - 다른 유틸/서비스 함수 호출 여부
4. **관련 모델/스키마**를 읽어 테이블명, 컬럼명, 연관관계 확인
5. 필요하면 기존 테스트 파일을 참고해 사전 데이터 세팅 방법 확인

### 2단계: 테스트 케이스 설계

아래를 분류해 **개발자에게 먼저 보여주고 피드백을 받는다**:

```
## 테스트 케이스 설계: {METHOD} {URL}

### 인증
- 필요한 토큰/권한 종류: (일반 유저 / 어드민 / 시스템 등)

### 사전 데이터
- {어떤 데이터가 DB에 있어야 하는지}

### 테스트 목록
| # | 유형 | 테스트명 | 입력/상태 | 기대 결과 |
|---|------|---------|----------|----------|
| 1 | 성공 | ... | ... | 200 + ... |
| 2 | 실패 | ... | ... | 401 |
| ... |

### 질문
- {비즈니스 로직에서 확인이 필요한 부분}
```

**함수당 최대 10건**. 중복 커버리지는 작성하지 않는다.

**작성하지 않는 테스트** (이 규율이 이 스킬의 핵심 — 스택과 무관하게 지킨다):

- **정당화 불가**: 모든 테스트는 "이 테스트가 없으면 어떤 버그를 놓치는가?"에 답할 수 있어야 한다. 답이 없으면 작성하지 않는다.
- **인증 미들웨어 반복**: `토큰 없음 → 401`은 도메인당 1개 파일에서만 검증. 모든 API마다 반복하지 않는다.
- **프레임워크 동작 테스트**: 프레임워크가 JSON을 파싱하는지, ORM이 쿼리를 만드는지 등 프레임워크가 보장하는 동작은 테스트하지 않는다.
- **단순 CRUD의 필드 나열**: `name`만 보내면 실패, `email`만 보내면 실패 — 이런 필드별 반복은 대표 1건으로 합친다.

### 3단계: 테스트 코드 작성

[`references/conventions.md`](./references/conventions.md)의 패턴을 **정확히** 따른다:

- 앱/라우터 진입점을 import하고 HTTP 클라이언트로 호출 (스택별 도구 → 커스터마이징 블록)
- DB/ORM 핸들은 프로젝트 규칙대로 import (상대경로가 아닌 프로젝트 alias 권장)
- 인증이 필요하면 이 프로젝트의 토큰/세션 생성 헬퍼 사용
- `TEST_PREFIX`를 **파일명과 동일하게** 설정 (데이터 격리용 — 다른 테스트와 절대 겹치지 않는 접두사)
- 파일 업로드가 있으면 스토리지 업로더 mock + 최소 바이너리 픽스처
- 날짜 의존 로직이면 날짜 고정 유틸 사용

**파일 위치**: 프로젝트의 테스트 배치 규칙을 따른다. 파일 1개 = API 동작 1개.
- 예: `src/{도메인}/__test__/{리소스}.{동작}.test.js`
- 예: 소스 옆(co-located) 또는 최상위 `test/` 하위 — 프로젝트 규칙대로 (커스터마이징 블록)

**병렬 실행 안전 (필수 — 보편 규율)**:
- `TRUNCATE`/`DROP` 등 테이블 전체를 비우는 조작 금지 — 다른 테스트 파일의 데이터를 날린다
- `TEST_PREFIX`로 유니크한 테스트 데이터 생성 (식별자·이메일 등에 접두사)
- `afterAll`(또는 상응하는 teardown)에서 **자기가 만든 데이터만** 삭제
- 테스트 중 생성한 리소스 ID는 배열로 추적해 cleanup

**절대 하지 않을 것**:
- DB를 mock하지 않는다 — 실제 테스트 DB를 사용 (외부 서비스만 mock)
- 테이블을 통째로 비우지 않는다 — 자기 데이터만 삭제
- 존재하지 않는 API 경로나 파라미터를 추측하지 않는다 — 라우팅/핸들러에서 확인
- 다른 API 엔드포인트의 동작에 의존하는 테스트를 만들지 않는다 — 사전 데이터는 DB/모델로 직접 세팅
- 단, 사전 데이터가 복잡하고 연관관계가 많으면(예: 복합 리소스 생성) 어드민 API 호출로 세팅해도 된다

### 4단계: 테스트 실행 및 검증

이 프로젝트의 **테스트 실행 명령**으로 방금 만든 파일만 돌린다 (명령은 커스터마이징 블록).

실패하면:
1. 에러 메시지를 읽고 원인 파악 (잘못된 URL? 누락된 사전 데이터? 응답 구조 불일치?)
2. 핸들러 소스를 다시 확인
3. 수정 후 재실행

### 5단계: 병렬 테스트 검증

단일 파일 통과 후, **기존 테스트들과 함께 실행해도 문제없는지** 검증한다(전체 또는 같은 도메인 몇 개와 함께).

**확인 사항**:
1. **데이터 충돌**: `TEST_PREFIX`가 충분히 유니크해 다른 파일과 간섭하지 않는가
2. **실행 순서 비의존**: 먼저/나중에 실행돼도 결과가 동일한가
3. **cleanup 누락**: teardown에서 자기 데이터를 제대로 삭제해 이후 테스트에 영향을 안 주는가
4. **공유 자원 경합**: 하드코딩된 유저/리소스 ID가 다른 테스트와 겹치지 않는가

**실패 시 조치**:
- 데이터 충돌 → `TEST_PREFIX`를 더 유니크하게 또는 사전 데이터 고유값 조정
- 순서 의존 → 다른 테스트 데이터 의존 제거, 자체 사전 데이터로 교체
- cleanup 불완전 → teardown에 누락된 삭제 추가
- 전체가 너무 느려 타임아웃 → 해당 파일만 기존 2~3개와 함께 실행해 검증

### 6단계: 테스트 코드 상단에 `// 문답전` 주석 추가

작성이 완료되면 파일 **최상단 1번째 줄**에 아래 주석을 추가한다:

```
// 문답전
```

이 주석은 개발자가 아직 이 테스트에 대한 문답을 완료하지 않았음을 뜻한다.
7단계 브리핑 → 8단계 문답이 모두 끝나면 제거한다. (주석 문법은 언어에 맞게 — `#`, `//`, `<!-- -->` 등)

### 7단계: 개발자 브리핑 (필수)

작성이 끝나면 **반드시** 아래 형식으로 개발자에게 설명한다. 이 단계를 절대 건너뛰지 않는다.

```
## 테스트 브리핑: {METHOD} {URL}

### 이 API가 하는 일
- {엔드포인트의 비즈니스 목적 1~2문장}
- 인증: {유저/어드민/시스템/없음}
- 주요 흐름: {요청} → {처리 단계} → {응답}

### 사전 데이터 구조
- {테스트를 위해 DB에 넣은 데이터와 그 이유}
- {테이블 간 관계가 있다면 간단히}

### 핸들러 분기 커버리지
핸들러의 주요 분기(if/throw/early return)와 각각을 커버하는 테스트를 매핑한다.

| 위치 | 분기 조건 | 커버하는 테스트 |
|------|----------|--------------|
| L25 | `if (!req.user.id)` → Unauthorized | #2 실패 - 미로그인 |
| L30 | `if (!title)` → BadRequest | #3 실패 - 필수값 누락 |
| L45 | `if (files.length > 10)` → 제한 | - (미커버) |

### 테스트가 검증하는 것
| # | 테스트명 | 이 테스트가 없으면 놓치는 버그 |
|---|---------|---------------------------|
| 1 | 성공 - ... | {구체적 회귀 시나리오} |

### 테스트하지 않은 것 (Known Gaps)
- {미커버 분기와 그 이유 — 위 표에서 "-"인 항목}
- {시나리오 테스트로 커버해야 할 부분}

### 개발자 확인 체크리스트
- [ ] 사전 데이터가 실제 서비스 상태를 잘 반영하는가?
- [ ] 에러 케이스의 조건이 실제 비즈니스 룰과 맞는가?
- [ ] 본인만 아는 엣지 케이스가 빠져있지 않은가?
- [ ] 응답 필드와 값이 클라이언트가 기대하는 것과 일치하는가?
```

### 8단계: 테스트 이해도 문답 (필수)

브리핑 후, 개발자가 테스트 코드를 **정말로 이해했는지** 확인하는 문답을 진행한다.
개발자가 직접 답해야 다음으로 넘어간다. (이 킷의 목적 — 개발자를 루프 안에 남겨두기 — 을 실현하는 핵심 단계)

#### 파트 A: 테스트 구조 이해 (setup / teardown / 사전 데이터)

셋업·정리 로직을 이해하는지 확인한다. 아래 3가지를 **각각 1문제씩** 질문한다:

- **Q1. setup(beforeAll) 질문** — 셋업에서 무슨 작업을 왜 하는지
- **Q2. teardown(afterAll) 질문** — 정리에서 무엇을 왜 정리하는지
- **Q3. 사전 데이터 질문** — 어떤 데이터를 넣었고, 각각 어느 테스트 케이스를 위해 필요한지

**⚠️ 질문 설계 시 금지 사항**

답이 **"격리성 보장"**, **"전체 삭제 금지"**, **"다른 테스트에 영향 안 주려고"**, **"데이터 정리"** 같은
일반론으로 귀결되는 질문은 하지 않는다. 컨벤션에 이미 있는 뻔한 답이며 개발자가 이미 안다.

대신 **이 테스트 파일에만 고유한 설계 결정**을 묻는다:
- ❌ "teardown에서 왜 이 순서로 삭제하나요?" → 답: "FK 때문에" (뻔함)
- ❌ "왜 전체 삭제를 안 쓰나요?" → 답: "병렬 안전성 때문에" (뻔함)
- ✅ "이 테스트에서 참조 리소스를 1개만 미리 만드는 이유는? 각 테스트마다 새로 만들면 안 되나요?"
- ✅ "`createVotePostData` 헬퍼가 옵션 3개로 고정돼 있는데, 어떤 테스트 케이스를 위한 선택인가요?"
- ✅ "userA와 userB를 분리한 이유는? 하나로는 왜 안 되나요?"

일반 컨벤션은 `references/conventions.md`에 있다. 문답은 개발자가 **본인이 작성한 코드의 의도**를
설명할 수 있는지 확인하는 자리이지, 컨벤션 암기 테스트가 아니다.

각 질문에 대해:
- 맞으면 → 다음 질문으로
- 틀리거나 모호하면 → 해당 코드 블록을 보여주며 구체적으로 설명한다

#### 파트 B: AI가 놓친 케이스 찾기 (2문제)

AI가 작성한 테스트가 완벽하지 않을 수 있다. 개발자가 비즈니스 로직을 실제로 이해하는지,
AI가 커버 못 한 엣지 케이스를 스스로 인지하는지 확인한다. **핸들러의 미커버 분기나 실서비스 엣지
케이스를 힌트로 제시**해 생각 방향을 잡아준다.

```
Q4. 이 테스트에서 AI가 놓친 케이스가 있을까요?
    (힌트: {핸들러의 특정 분기 또는 비즈니스 상황})

Q5. 실서비스에서 이 API를 쓸 때 현재 테스트가 잡지 못하는 상황이 있을까요?
    (힌트: {동시성, 데이터 정합성, 권한 등 실서비스 관점})
```

각 질문에 대해:
- 실제 미커버 케이스를 짚으면 → "맞습니다" + 왜 중요한지 보충
- "없다"/모호하면 → 핸들러의 미커버 분기를 짚고, 실서비스에서 어떤 문제가 될지 설명
- 이미 커버한 케이스를 말하면 → 해당 테스트가 이미 커버함을 코드로 보여준다

#### 마무리

5문제가 끝나면:
1. **"이 테스트 파일이 보호하는 핵심 동작을 한 문장으로?"** 으로 마무리
2. 완료되면 → 9단계

### 9단계: `// 문답전` 주석 제거 (필수)

문답이 끝나면 파일 최상단의 `// 문답전` 주석을 **제거**한다.
주석이 없다는 것은 개발자가 이 테스트에 대한 이해를 완료했음을 뜻한다.
