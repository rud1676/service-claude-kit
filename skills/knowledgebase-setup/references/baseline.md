# 기준 설계 — 왜 이 모양인가

`knowledgebase-setup`이 세우는 지식 베이스의 **기본형**과 그 근거. 인터뷰(8갈림)로 바꿔 끼우는 건 영역·타입 목록·확정 입구·운전 방식이고, 아래 네 가지는 **바꾸지 않는 뼈대**다.

---

## 뼈대 1. 층은 "누가 쓰나"로 나눈다

```
schema/   규칙·타입·영역        사람만 쓴다 (에이전트는 PR 제안만)
raw/      원본 (텍스트 추출본)   추가만. 수정·삭제 금지
<영역>/    페이지                에이전트가 주로, 사람도 쓴다
index.md  목차·확정 대기         스크립트가 생성
```

**`raw/`가 추가만인 이유**: 페이지의 모든 문장이 `raw/`를 가리킨다. 원본이 바뀌면 출처 표기가 **거짓**이 된다. 그리고 페이지가 틀렸을 때 되돌아갈 바닥은 `raw/` 하나뿐이다. 중복·손상된 원본도 지우지 않고 주석을 단다.

원본 바이너리(pdf·docx·이미지)는 넣지 않고 텍스트만 둔다. 개인정보는 **적재 단계에서** 가린다 — 페이지 단계에서 지우면 이미 늦다.

## 뼈대 2. 사실에는 등급과 출처가 붙는다

| 등급 | 근거 | 본문 표기 |
|---|---|---|
| **확정** | 결정권자의 확인 원문, 또는 결정권자가 승인한 PR | `[확인:<이름> YYYY-MM-DD]` |
| **문서상** | 초안·외부 자료·DB 조회·내 관찰. 확인 없음 | `[src:n]` |
| **추론** | 근거 없음 | `[추론]` |

- `[src:n]`의 `n`은 그 페이지 `sources` 목록의 순번(1부터). 린트가 범위를 검사한다.
- **에이전트는 스스로 확정을 올리지 못한다.** 입구는 사람뿐이다. 이 잠금이 없으면 등급·출처·린트 전체가 장식이 된다.
- **특정 상태값은 확정만 허용한다** (`types.json`의 `confirmed_only`). 예: 결정의 "확정됨", 정책의 "시행 중". 근거가 없으면 초안 상태로 두고 `confirm_pending: true`를 붙인다.
- **등급을 낮추는 것 ≠ 사실을 빼는 것.** 두 원본이 숫자를 다르게 적었으면 **둘 다 적고** 등급을 낮춘 뒤 `question`을 만든다. 하나를 고르지 않는다.
- 진 쪽은 지우지 않고 본문 `## 이력` 으로 내리고, 이긴 쪽 `supersedes`에 적는다.

### 충돌 우선순위 (회사마다 1·2번만 바꿔 끼운다)

1. 더 최신의 **결정권자 확인 원문** → 2. **공식 기록**(그 업종의 체결·등기·승인 문서) → 3. 더 최신의 회의록·결정 → 4. 계획·제안 문서(버전 높은 쪽) → 5. 대화·채팅

같은 단계면 최신이 이긴다.

## 뼈대 3. 규격은 두 벌, 검사는 코드로

사람이 읽는 `schema/rules.md` 와 기계가 읽는 `schema/types.json` **두 벌**을 둔다. **둘의 상태값이 갈라지면 린트가 실패**하게 만든다.

> "무엇을 하라"는 산문으로 통하지만, **"매번 빠짐없이 확인하라"는 산문으로 지켜지지 않는다.**

그래서:

- **계산할 수 있는 칸은 스크립트가 채운다** (`id`·`created`·등급 표기 개수 등). 에이전트가 판단해 채우면 값이 제각각이 된다. 두 번 돌려도 결과가 같아야 하고, 이미 있는 값은 덮지 않는다.
- **린트 최소 5개** — ① `sources` 파일 실재 ② 링크 대상 실재 ③ 필수 칸·허용 상태값·영역 실재·id 중복 ④ `[src:n]`의 n이 범위 안 ⑤ 확정만 허용 상태값인데 근거 없음(단 `confirm_pending`이면 통과).
- **자동 칸·린트는 첫날에 넣는다.** 나중에 넣으면 쌓인 페이지 전부를 소급해야 한다. 페이지가 0~2개인 세팅 직후가 가장 싸다.

## 뼈대 4. 분류 축은 셋뿐, 자유 태그는 두지 않는다

| 축 | 질문 | 값의 출처 |
|---|---|---|
| `type` | 이 페이지가 지식에서 맡는 역할은? | `types.json` 고정 목록 |
| `area` | 어느 업무 영역인가? (라우팅용, 칸막이 아님) | `areas.md` |
| `status` | 생애주기 어디인가? | 타입별 허용값 |

폴더는 저장 위치일 뿐이고 의미는 이 셋이 진다. **자유 태그는 두지 않는다** — 동의어와 낡은 값으로 검색을 흐린다. 그 역할은 이 셋과 명시적 `[[링크]]`가 한다.

## 타입 기본셋 5개

업종 무관하게 거의 항상 필요한 다섯이다. **여기서 시작해 모자랄 때만 늘린다.**

| 타입 | id | 허용 상태값 (**굵게** = 끝) | 확정만 허용 | 무엇 |
|---|---|---|---|---|
| `decision` | `dec-` | proposed · **decided** · **reversed** | `decided` | 누가 언제 무엇을 결정했나, 버린 대안 |
| `question` | `q-` | open · **answered** · **closed** | — | 모순·공백·확인 필요. 충돌의 배출구 |
| `concept` | `c-` | active · **retired** | — | 용어·정의·계산식·판정 기준 |
| `spec` | `s-` | draft · active · **superseded** | `active` | 기능·정책의 현재 정본. 초안으로 들어와 확인 후 시행 |
| `event` | `e-` | open · in-progress · **closed** · **cancelled** | — | 일어났거나 일어나야 할 일 한 건 |

- **`concept`이 가장 오래 산다.** 코드·제품이 바뀌어도 "무엇을 재려 했는가"는 여기 남는다. 그 회사의 핵심 도메인이 뭐든 거기서부터 채운다.
- **`question`을 빼지 말 것.** 이게 없으면 에이전트가 충돌을 만날 때마다 임의로 하나를 고른다.
- 타입을 늘리는 기준: 맞는 타입이 없는 페이지가 **같은 성격으로 3건** 모이면 신설을 제안하고 사람 승인으로 확정한다. 그전엔 `event`에 둔다. **1건 때문에 타입을 만들지 않는다.**

## 프론트매터 기본형 — 사람 6칸 + 자동 3칸

```yaml
---
type: decision
title: <제목>
status: decided
area: <영역>
sources: [raw/confirmations/2026-10-16-....md]
updated: 2026-10-16
# ── 조건부
confirmed_by: <이름>
confirmed_at: 2026-10-16
confirm_pending: true      # 확정 대기 중 (린트가 조르지 않게)
supersedes: []
# ── 스크립트가 채움
id: dec-0003
created: 2026-10-16
grade_marks: 확인 1 · 출처 2 · 추론 0
---
```

`sources`가 비면 페이지를 만들 수 없다 — `question`만 예외.

**본문 규칙**: 다른 페이지 참조는 `[[영역/파일명]]`만(URL·상대경로 금지). 날짜는 `YYYY-MM-DD`. **숫자는 원본 표기와 단위를 유지**한다(`월 1,200만 원`을 `12000000`으로 바꾸지 않는다). 페이지 1,500자 안팎, 넘으면 하위 페이지로.

**등급을 세는 게 아니라 표기를 센다.** 같은 `[src:n]`도 근거가 공식 기록이면 확정, 초안이면 문서상이다. 그래서 자동 칸은 등급이 아니라 **표기 개수**(`grade_marks`)를 센다.

## 처음엔 안 짓는 것 (없어진 게 아니라 **아직 안 지은 것**)

소수 인원(1~3명)에서 이걸 베끼면 규칙만 무거워지고 아무도 안 쓴다. `rules.md`에 "안 지었다"고 명시해, 반년 뒤 "왜 없지"가 아니라 "이제 꺼낼 때"가 되게 한다.

| 안 짓는 것 | 언제 꺼내나 |
|---|---|
| 승인 2인 · 이의 기간 · 규약 통지 절차 | 쓰는 사람이 4명을 넘고 권한이 갈릴 때 |
| 실행 층(발송·서명·송금 액션 규격·제출기·영수증) | **맨 마지막.** 사실이 틀린 상태에서 실행부터 하면 틀린 일을 빠르게 한다 |
| 즉시·일일·주간 브리핑 | 사람이 부르는 걸로 부족해질 때 |
| 체인(이 유형 다음엔 무엇이 와야 하나) · 표준 운영법↔인스턴스 짝 | 같은 유형 업무가 반복되는 게 눈에 보일 때 |
| 외부 미러(문서 도구·Publish) | 규칙이 안정된 뒤. 경로가 찾기 키가 되어 리네임마다 고아 페이지를 보관 처리해야 한다 |
| 갱신 이력 절 **필수화** | 미러를 둘 때. 미러가 없으면 git 이력·커밋 메시지로 충분하다 |

## 운영 원칙 (사람이 1명이어도 지킨다)

- **조용한 성공 금지.** 사람의 행동이 무효가 됐으면(중복이라 적재 안 함, 추출이 빈약함, 마스킹으로 지움, 확정 대기) **그 사람이 행동한 자리로 돌려준다.**
- **"했습니다"를 믿지 않는다.** 커밋 해시·파일 안 문자열 수·API 응답으로 확인한다.
- **답을 채팅에 흘리지 않는다.** 새로 종합한 내용은 페이지로 남긴다.
- **위키 먼저.** 답하기 전에 지식 베이스를 읽고, 없으면 *"지식 베이스에 없음"* 이라고 말한 뒤에만 추론한다.
- **AI가 만든 페이지를 다시 원자료처럼 취급하지 않는다.** 근거가 순환한다.
- **사람이 직접 쓴 분석·관찰을 자동 재생성으로 덮어쓰지 않는다.**

## 구현할 때 미리 알 것

- git 날짜는 **현지 시각으로 바꿔** 읽는다. 서버가 UTC로 커밋하면 새벽 커밋이 전날로 찍힌다.
- "먼저 생긴 쪽"은 날짜가 아니라 **시각**으로 가른다. 같은 날 두 페이지를 날짜만 보고 가르면 이름순이 되어 판정이 뒤집힌다.
- 번호(`q-007` 등)는 사람·에이전트가 붙이고 **스크립트는 고르지 않는다.** 겹치면 비워 두고 보고만 한다 — 재번호는 링크까지 건드리는 사람의 결정이다.
- 빈 폴더는 git이 추적하지 못한다. 규칙이 가리키는 경로엔 **`.gitkeep`** 을 넣는다.
