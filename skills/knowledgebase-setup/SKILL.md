# knowledgebase-setup — 회사 지식 베이스 세우기

사람과 여러 에이전트가 **같은 지식**을 보고, **근거를 확인**하고, **고칠 수 있게** 만드는 저장소를 세운다.

> 한 문장: **원본은 추가만 하고, 페이지는 원본을 가리키며, 확정은 정해진 사람만 찍고, 검사는 코드가 한다.**

## 워크스페이스 `context/` 와 무엇이 다른가 (먼저 읽을 것)

이 킷에는 이미 워크스페이스 `context/`가 있다. **둘은 다른 물건이고, 섞으면 둘 다 망한다.** 지식 베이스의 페이지 층은 `wiki/`라고 부른다 — 이름부터 갈라 두어 "어느 쪽 문서냐"가 경로만 보고 갈리게 한다.

| | 워크스페이스 `context/` | 지식 베이스 `wiki/` (이 스킬) |
|---|---|---|
| 담는 것 | **코드를 읽으면 확인되는 것** — 구조, 데이터 흐름, 동작 원리 | **코드를 읽어도 안 나오는 것** — 사람의 결정, 도메인 정의, 운영 수치, 외부 사실 |
| 원천 | 코드 자체 (언제든 재확인 가능) | 사람의 말·문서·외부 자료 (사라지면 확인 불가) |
| 등급·출처 | 불필요 | **필수** (`[확인:…]` / `[src:n]` / `[추론]`) |
| git | 워크스페이스는 비-git | **독립 git repo** (PR이 검토 자리) |
| 관리 | `explain` 스킬 | 이 스킬 + `knowledgebase-raw-scraping-github` |

**라우팅 판정 질문 둘** — 이 두 줄이 경계의 전부다. 지식 베이스를 세울 때 `rules.md`에 반드시 넣는다.

1. 코드를 다시 읽으면 확인되는 사실인가? → 워크스페이스 `context/` (그 프로젝트가 다른 이름을 쓰면 그 이름)
2. 사람이 정했거나 밖에서 온 사실인가? → **지식 베이스** (+ 출처 표기)

## 언제 / 어떻게

- `/knowledgebase-setup` 또는 "지식베이스 만들어줘" 같은 **명시 호출**에만 발동한다.
- 이미 `schema/rules.md`가 있는 repo에서 부르면 **새로 만들지 않고** "개정 모드"로 간다(§5).
- 인터뷰는 **`grill-me` 스킬을 `Skill` 도구로 호출**해서 한다. 직접 질문 쏟아내지 않는다.

## 단계

### 0. 선행 확인 (묻기 전에 내가 조사한다)

인터뷰 질문을 코드로 답할 수 있으면 묻지 않는다. 먼저 확인할 것:

| 확인 | 어떻게 | 왜 |
|---|---|---|
| 지식 베이스 repo가 이미 있나 | `ls`, `git remote -v`, 커밋 수 | 있으면 개정 모드 |
| 둘 곳 | 기본 `repository/knowledgebase/`. 프로젝트가 쓰는 이름이 있으면 그걸 따른다 | 경로는 규칙 문서에 박히므로 먼저 정한다 |
| **이미 쌓인 기억 자산** | `context/` `study/` `decision-log/` `plan/` 각 repo의 코드위키 — **개수와 줄 수를 센다** | §인터뷰 ③의 선택지를 숫자로 제시해야 한다 |
| 자동 수집이 가능한 원천 | Slack/Figma MCP 연결 여부, `gh` 인증, DB 조회 스킬, 서비스 표면(라우트·도메인 폴더) | §인터뷰 ②에서 "없는 원천"을 가짜로 열지 않기 위해 |
| 확정을 찍을 사람 | 누가 결정권자인가, 그 사람이 쓰는 채널이 기계가 읽히나 | 확정 입구가 없으면 지식 베이스는 영원히 초안만 쌓는다 |

원천 확인은 **실제로 호출해 본다.** "Slack 있겠지"로 적지 말고 채널을 조회해 그 워크스페이스가 이 회사 것인지 확인한다(다른 회사 워크스페이스가 붙어 있는 경우가 흔하다).

### 1. 인터뷰 — `grill-me` 로 8갈림 확정

`Skill` 도구로 `grill-me`를 호출하고, **아래 8개를 순서대로, 한 번에 하나씩** 파고든다. 각 갈림에 **추천과 그 근거(0단계에서 확인한 사실)** 를 곁들인다.

| # | 갈림 | 기본 추천 | 추천 이유 / 반대쪽 함정 |
|---|---|---|---|
| ① | **범위** — 회사 전체 / 제품만 / 결정만 | 회사 전체 | 좁게 시작하면 채널·수익·대외가 갈 자리가 없어 결국 다른 곳에 쌓인다 |
| ② | **원본 원천** — 무엇이 글로 들어올 수 있나 | 실제 확보된 것만 | 안 들어오는 영역은 `[추론]`만 쌓이고 린트가 계속 조른다 |
| ③ | **기존 자산** — 이관 / 경계 선언 / 새로 시작 | 경계 선언 + 점진 이관 | 전부 흡수는 설계 검증보다 노동이 앞선다. 새로만 시작하면 정본이 둘이 될 위험을 §④로 막아야 한다 |
| ④ | **새 사실 라우팅** | **원본 여부로 가름**(위 2줄) | 이게 없으면 같은 결정이 두 곳에 산다 — 가장 큰 실패 모드 |
| ⑤ | **확정 입구** — 누가 어디서 찍나 | 결정권자의 **원문 적재** + **PR 승인** | 에이전트·대리인이 확정을 올리면 등급 체계가 장식이 된다 |
| ⑥ | **영역(area)** — 몇 개를 어떻게 | 5개 이하로 시작(넓게 열려면 "선언만, 폴더는 첫 페이지 때") | 빈 영역이 많으면 운영 중인 것처럼 안 보이고 린트가 공백을 쏟는다 |
| ⑦ | **운전 주체** — 수집·컴파일·린트를 누가 | 사람이 부르고 **린트만 자동** | 전부 자동은 아침마다 사람이 치우게 된다. 그 팀이 전에 자동 스케줄을 끄은 전례가 있으면 결정적 근거다 |
| ⑧ | **사람의 화면** — 미러/전용 화면 | 없음, md + PR | 미러를 두면 경로가 찾기 키가 되어 리네임마다 고아 페이지를 보관 처리해야 한다 |

인터뷰 중 **반대쪽 함정을 반드시 말한다.** 사용자가 추천과 다르게 고르면 그대로 따르고, **그 선택이 남기는 구멍을 다음 질문으로 막는다**(예: ③에서 "새로 시작"을 고르면 ④를 반드시 물어야 한다).

### 2. 산출 — `assets/` 템플릿을 인터뷰 답으로 채운다

```
<KB_ROOT>/
├── README.md          입구 — 한 장 요약, 라우팅 표, 확정 절차
├── schema/
│   ├── rules.md       규칙 정본 (층·라우팅·등급·프론트매터·타입·린트·§왜 이렇게)
│   ├── areas.md       영역 선언 + 무엇이 들어오나 + 주 원천
│   └── types.json     기계 판독 규격 (타입·허용 상태값·자동 칸·확정만 허용 상태값)
├── raw/               원천별 하위 폴더 + 각 폴더에 .gitkeep
├── wiki/              컴파일된 페이지 층 — 페이지는 여기 아래에만 산다
│   └── <영역>/        첫 페이지가 생길 때 만든다
└── index.md           목차·확정 대기 (스크립트가 생성)
```

- **페이지는 `wiki/<영역>/` 아래에만** 둔다. 영역 폴더를 루트에 펼치지 않는다 — 루트에는 `schema/`·`raw/`·`state/`·작업 공간처럼 페이지가 아닌 것도 함께 살아서, 페이지 판별이 "나머지 전부"라는 빼기가 되고 루트 폴더가 늘 때마다 `lint_ignore`를 고쳐야 한다. `wiki/` 하나로 묶으면 "`wiki/` 아래 = 페이지"로 끝난다.
- 페이지 참조는 `[[wiki/<영역>/<파일명>]]` — repo 루트 기준 경로라 링크 문자열이 곧 파일 위치다.

- 템플릿: `assets/README.md` · `assets/rules.md` · `assets/areas.md` · `assets/types.json`. `{{중괄호}}` 자리를 인터뷰 답으로 바꾼다.
- 기준 설계(왜 3층인가, 등급은 왜 셋인가, 타입 기본셋, 뺀 것 목록)는 **`references/baseline.md`** 를 읽는다.
- `raw/` 하위 폴더는 **②에서 실제로 확보된 원천만** 만든다. 없는 원천 폴더를 미리 만들지 않는다.
- 빈 폴더는 git이 추적하지 못하므로 **`.gitkeep`** 을 넣는다 — 규칙 문서가 그 경로를 가리키는데 repo에는 없는 상태를 막는다.
- **`rules.md`의 마지막 절은 "§왜 이렇게 정했나"** 다. 8갈림의 **고른 쪽 / 버린 쪽 / 버린 이유**를 표로 남긴다. 이게 없으면 반년 뒤 "왜 이렇게 불편하게 해놨지"에 답할 수 없다.

### 3. git repo로 세우기

```bash
cd <KB_ROOT> && git init -b main
# remote 가 있으면 연결만 하고, 첫 커밋은 사용자 승인 후
```

커밋·push·PR은 **사용자가 명시 요청할 때만** 한다(킷 공통 규칙). 다만 *"첫 커밋을 올릴까요?"* 는 물어본다 — 커밋 0개 repo는 다른 사람이 clone해도 규칙을 못 읽는다.

### 4. 시험 1건 — 규칙은 써 보기 전엔 다 그럴듯하다

세팅 직후 **실제 페이지 1~2개**를 끝까지 만들어 본다. 권장 조합:

- 결정 1건 (`decision`) — 원문을 `raw/`에 넣고, 등급 표기를 달고, 확정 입구를 실제로 통과시켜 본다
- 그 회사의 **핵심 자산 타입** 1건 (`concept`) — 용어·계산식·판정 기준처럼 "코드가 바뀌어도 남아야 하는 것"

여기서 걸리는 것(필수 칸이 과하다, 등급을 못 정하겠다, 영역이 애매하다)이 **규칙의 실제 결함**이다. 바로 `rules.md`를 고친다.

### 5. 개정 모드 (이미 `schema/rules.md`가 있을 때)

- 새로 쓰지 않는다. **무엇을 왜 바꾸는지**만 묻고 해당 절을 고친다.
- `types.json`과 `rules.md`의 **상태값이 갈라지면 린트가 실패한다** — 둘을 항상 같이 고친다.
- 타입·영역을 늘릴 땐 **"같은 성격 3건이 모였나"** 를 먼저 확인한다. 1건 때문에 타입을 만들지 않는다.
- 규칙을 바꾸면 기존 페이지에 필요한 보완을 목록으로 뽑아 보고한다. 조용히 소급하지 않는다.

## 주의점

- **등급의 입구를 사람으로 묶는다.** 에이전트가 스스로 "확정"을 올릴 수 있으면 등급·출처·린트가 전부 장식이 된다. `types.json`의 `confirmed_only` 상태값이 그 잠금 장치다.
- **충돌하면 고르지 않는다.** 두 원본이 숫자를 다르게 적었으면 **둘 다 적고** 등급을 낮추고 `question` 페이지를 만든다. 자동으로 최신을 택하는 규칙은 넣지 않는다.
- **기계 판독 규격·자동 칸·린트는 첫날 세트다.** 나중에 넣으면 쌓인 페이지 전부를 소급해야 하고, 그사이 생긴 규격 밖 값을 사람이 하나씩 정리해야 한다. 페이지가 0~2개인 **지금이 가장 싸다.**
- **뺀 것은 없어진 게 아니라 안 지은 것**이라고 `rules.md`에 적는다(실행 층·승인 게이트·브리핑·체인 등). 나중에 필요해질 때 "왜 없지"가 아니라 "이제 꺼낼 때"가 된다.
- 소수 인원(1~3명)에 **승인 2인·이의 기간·전용 검토 화면**을 베끼지 않는다. PR 리뷰 하나로 충분하다.
- 페이지가 아니라 **`raw/`가 바닥**이다. `raw/`는 추가만 — 수정·삭제하면 모든 출처 표기가 거짓이 된다.
