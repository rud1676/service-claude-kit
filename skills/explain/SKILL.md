"이 PR 정리해줘", "방금 만든 거 왜 이렇게 짰는지 문서로 남겨줘", "이 diff 머지 전에 배경까지 정리해줘"처럼 **자기 변경을 산출물로 남길 때** 사용. — 단, "이 에러 왜 나는지", "이 함수 뭐 하는지", "X가 뭔지" 같이 그냥 궁금해서 묻는 **개념·에러·코드 설명 요청에는 발동하지 않는다**(그건 일반 대화/학습이며, 남길 문서가 아니다).
---

이 스킬은 코드(특히 AI가 대신 짠 코드)를 **검증이 아니라 '참여'를 위해** 이해하도록 돕는다. 목표는 읽는 사람 머릿속에 풍부한 개념 모델을 심어 인지 부채(cognitive debt)를 막는 것이다. 그래서 diff를 나열하는 데 그치지 않고, **코드만 봐선 안 보이는 것**(왜 이 결정인가 / 어떤 대안을 버렸나 / 무슨 가정을 깔았나 / 어디까지 영향을 주나)을 복원해 남긴다.

**왜 이 스킬이 필요한가.** AI는 코드를 인간이 읽어낼 수 없는 속도로 쏟아낸다. 그래서 개발자는 diff를 쓱 훑고 "아, 이해했네" 하고 넘어가는데 — 이건 대부분 *낯익음(familiarity)*을 *이해(understanding)*로 착각한 것이다. **읽기는 이해가 아니고, 인간은 스스로를 잘 속인다.** 이 스킬은 그 착각을 깨서, AI의 생산 속도에 **인간의 이해 속도를 맞추는 브레이크**다.

> 이 스킬의 산출물은 **프로젝트 지식**이라 `{WIKI}` 에 쌓인다. "이 리액트 훅 어떻게 동작해?"처럼 *내가 배우려고* 물어본 학습 기록은 성격이 달라 `study/` 에 따로 남기며(프로젝트 `CLAUDE.md` 규칙), 둘은 서로 섞거나 승격하지 않는다.

## 두 가지 모드 (자동 판별 + 오버라이드)

- **change** — 기존 시스템에 얹힌 델타(diff/PR). 무게중심: *뭐가 왜 바뀌었나*, 파급효과. 배경 = 주변 시스템.
- **creation** — 통째로 새로 짠 모듈/기능. 무게중심: *구조와 결정*, 왜 이 모양인가. 배경 = 풀려는 문제와 요구사항.
- 판별 기준: 신규 파일 비율·diff 규모로 자동 추정하되, 사용자가 "change/creation으로"라고 하면 그대로 따른다. 애매하면 한 줄로 물어본다.

## 설명 방식 (비유 · 시나리오)

읽는 사람 머릿속에 개념 모델을 심으려면, 코드 용어를 그대로 되풀이하지 말고 **일상의 언어로 치환**한다. 두 가지 도구를 함께 쓴다.

### 1) 비유 — 일상의 언어로 치환
낯선 개념은 이미 아는 것에 빗대 설명한다. 예: *"쿠버네티스의 파드(Pod)는 아파트 단지로 치면 '호(戶)'야. 컨테이너 하나하나는 그 호 안의 방이고."*

> ⚠️ **비유가 반드시 누락하는 진실을 함께 밝혀라.** 모든 비유는 어느 지점에서 반드시 깨진다 — 편하자고 버린 부분이 있기 때문이다. 비유를 쓴 문단 바로 뒤에 **"이 비유가 놓치는 것"** 을 한 줄 이상 붙여, 독자가 비유를 사실로 착각하지 않게 한다.
> 예: *"단, 이 비유는 '호는 고정되지만 파드는 언제든 죽고 새로 뜬다(ephemeral)'는 점을 놓친다. 파드는 이사 나갈 수 있는 호가 아니라, 필요할 때 지었다 허무는 임시 텐트에 가깝다."*

### 2) 시나리오 — 관점을 나눠 결과로 보여준다
추상적 설명 대신 **누가 · 어떤 상황에서 · 무엇을 겪는지**로 풀어라. 최소 두 관점을 쓴다.

- **개발자 관점** — 코드 선택이 개발/런타임에 어떤 차이를 만드는가.
  예: *"`useCallback`을 쓴 개발자 A는 리렌더마다 함수를 새로 만들지 않아, 이 코드를 거친 유저는 반응이 더 빠르게 느껴진다. 안 쓴 개발자 B는 매 렌더마다 함수를 재생성해 그만큼 비용을 더 낸다."*
- **유저 시나리오** — 최종 사용자가 실제로 체감하는 것.
  예: *"Next(SSR)를 택한 프로젝트는 유저 A 입장에서 첫 페이지가 서버에서 완성돼 오므로 초기 화면이 빨리 보인다. CSR만 쓴 쪽은 빈 화면 뒤에 자바스크립트가 받아진 다음에야 내용이 뜬다."*

## 절차

1. **스코프 확정** — 설명 대상을 정한다: `git diff`/브랜치/PR(change) 또는 특정 모듈·기능(creation). 대상이 불명확하면 먼저 묻는다.
2. **실제 코드 읽기** — 추측 금지. 모든 주장에 `파일:줄` 근거를 붙이되 **누르면 그 줄로 가는 링크 형식**으로 적는다: `[src/foo.ts:42](src/foo.ts#L42)`(범위는 `#L42-L50`). 진입점부터 데이터 흐름·호출 관계를 따라간다.
3. **도메인 판별** — 이 작업이 속한 도메인을 정하고, 위키의 대상 경로 `{WIKI}/{도메인}/<주제>.md` 를 결정한다.
4. **'안 보이는 것' 복원** — 결정 / 버린 대안 / 깔린 가정 / 파급 범위(blast radius)를 뽑아낸다. 특히 creation 모드에선 이게 코드 설명보다 값지다. 에이전트가 조용히 내린 선택을 정직하게 회고한다.
5. **설명 문서 작성·갱신** — 아래 "설명 문서 포맷"대로 위키 경로에 쓴다. 기존 문서가 있으면 덮지 말고 `## 후속 (날짜)` 로 이어 붙인다.
6. **decision-log 판단** — 판단이 갈렸거나 버린 대안이 있었던 결정만 골라, `{DECISION_LOG}/` 에 1건씩 append하고 설명 문서와 상호 링크한다. (없으면 이 단계는 건너뛴다 — 매번 남기지 않는다)
7. **인덱스 갱신** — `{WIKI}/README.md` 목차 표에 새 문서의 한 줄 설명을 추가한다(이미 있으면 갱신).
8. **마무리 — 만져보기 제안(항상 물어본다)** — 문서 작성이 끝나면 **반드시** 사용자에게 "이걸 직접 굴려볼 대화형 데모를 만들까요?"를 묻는다. 혼자 판단해 건너뛰지 않는다.

   **왜 하나 (마이크로월드의 목적):** AI가 순식간에 짠 코드는 "내 레포에 있지만 정작 나는 어떻게 도는지 모르는" 상태 — **인지 부채(cognitive debt)** — 를 남긴다. diff를 읽으면 갚는 것 같지만 그건 *낯익음*을 *이해*로 착각하는 함정이다(남 운전을 조수석에서 본다고 내가 운전할 수 있는 게 아니다). 만져보기는 이 부채를 **능동 조작으로 갚는 장치**다: 배포용 기능이 아니라 **오직 나만을 위한 일회용 시각 교보재**를 AI에게 만들게 해, 이번 변경의 동작 직관을 머릿속에 이식한다. (부채를 만든 AI에게 부채를 갚을 도구를 만들게 시키는 것.)

   아래 두 관문을 순서대로 통과할 때 후보다:
   - **관문 ① 이번 "이 변경"에 묶여 있는가?** — 기준은 '개념이냐 아니냐'가 아니라 **'방금 AI가 내 레포에 한 그 변경을 이해하려는 것이냐'**다.
     - 내 실제 코드에 일어난 일을 내 실제 구조로 보여주면(내가 짠 상태머신이 실제로 어떻게 돌지, AI가 **내** 컴포넌트 트리에 넣은 최적화가 리렌더를 실제로 어떻게 줄였는지) → **explain의 만져보기로 적합**. 개념(useCallback 등)을 다뤄도 이 변경에 묶여 있으면 explain에 남는다.
     - 반면 이 변경과 무관한 **교과서용 일반 개념 데모**("useCallback이란 게 원래 뭔가")를 만들고 싶은 것 → 그건 `study` 소재다. 여기서 만들지 말고 study로 돌린다.
   - **관문 ② 정적인 글·스크린샷으로 안 잡히는 동적인 게 있는가?** — 시간에 따라 바뀌거나(상태 전이) 입력에 따라 분기(조건)하거나 데이터가 흐르거나 **공간·좌표·레이어가 얽히면** → 그 **한 메커니즘만** 단일 HTML/`.tsx` 대화형 아티팩트(마이크로월드)로 뽑는다. 정말 아무 동적 요소도 없으면(카피·색상값만 바뀐 정도) 스킵을 권하고 before/after 스크린샷으로 대신한다.
   - **UI를 크게 바꾼 작업은 스킵이 아니라 1순위 후보다.** 큰 UI 변경일수록 바뀐 **좌표계·레이어·z-index·상태 전이**가 diff로는 절대 안 잡히기 때문이다. 만질 소재는 "보이는 화면(픽셀)"이 아니라 **화면을 그렇게 만들어낸 좌표·판정·흐름 로직**이다. 예: 요소를 마우스로 드래그하며 레이어/z-index 변화를 보는 시뮬레이터, 한 단계씩 눌러 파일이 어디로 옮겨가고 화면이 어떻게 바뀌는지 보는 버튼 게임. 앱 껍데기를 복붙하지 말고 그 로직만(또는 before/after 토글 자체를) 떼어낸다.
   - 원하면 만져보기 대신(또는 함께) 핵심을 짚는 5문항 안팎 퀴즈로 이해를 점검할 수도 있다.

## 설명 문서 포맷

**왜 이 순서인가 (교육학 원리).** 좋은 선생님은 결과물(코드)부터 들이밀지 않는다 — **배경 → 직관 → 그다음에 세부**다. 아래 포맷의 섹션 순서는 이 원리를 그대로 따른 것이니, 순서를 지켜서 쓴다.

```
# <주제>   (mode: change | creation)
> 대상: <repo/브랜치/PR 또는 모듈>   · 작성: <YYYY-MM-DD>   · 근거 커밋: <hash>

## 직관 / TL;DR      — 한두 문단. 벽글 방지, 큰 그림(무엇을/왜) 먼저. 핵심 개념은 비유로 치환하고, 바로 "이 비유가 놓치는 것"을 붙인다.
## 배경지식          — 이걸 이해하려면 먼저 알아야 할 것.
## 어떻게 동작하나    — 파일 목록을 나열하지 말고, *이 파일을 왜 바꿨는지*를 이야기(서사)로 엮는다. 데이터가 진입점부터 어디로 흐르는지 따라가며 단계별 흐름 + 클릭형 `[파일:줄](파일#L줄)` 근거. 필요하면 mermaid.
## 시나리오로 보기    — 개발자 관점 + 유저 시나리오로 "누가 무엇을 겪는지" 풀어낸다.
## 관련 결정          — 이 코드가 이런 모양인 이유. 상세는 → decision-log 링크.
## (옵션) 만져보기    — 이번 변경에 묶인 동적 메커니즘(상태 전이·조건 분기·데이터 흐름·좌표/레이어)을 오직 나를 위한 일회용 마이크로월드로 뽑은 대화형 아티팩트 링크. 화면(픽셀) 재현이 아니라 그 밑 로직 하나. 큰 UI 변경일수록 1순위.
## 다음에 할 수 있는 것 / 건드릴 지점   — '참여' 지향 마무리. 여기에 뭘 붙이거나 어디를 고치면 되는지.
## 3줄 요약          — 이 작업이 무엇을/왜/무엇을 남겼는지 딱 3줄. 이 문서 전체를 못 읽어도 여기만 보면 되게.
```

## decision-log 포맷 (판단이 갈렸을 때만)

append-only 아카이브. 거의 안 고친다. 나중에 "이 결정 언제·왜 났지?"에 빠르게 답하기 위한 것.

```
# <YYYY-MM-DD> · <결정 제목>
- 맥락  : 왜 이 결정이 필요했나
- 택함  : 무엇을        → 정본: {WIKI}/{도메인}/<주제>.md
- 안 택함: 검토했지만 버린 대안들 + 각각 왜 버렸나      ← 이 문서의 심장
- 가정  : 깔린 전제 (이게 틀리면 이 결정도 뒤집힘)
- 관련  : 티켓 / PR
```

## 신뢰성 규칙 (지키지 않으면 위키를 믿을 수 없게 된다)

- **모든 주장에 `파일:줄` 근거 — 누르면 그 줄로 가는 링크로.** `[src/foo.ts:42](src/foo.ts#L42)` 형식. 추측·기억에 의존하지 않는다.
- **비유엔 항상 "놓치는 것"을 붙인다.** 비유만 남기면 독자가 그걸 사실로 착각한다.
- **diff는 나열이 아니라 서술이다(literate).** "파일 A·B·C 바뀜" 식 목록 금지. 파일마다 *왜 이렇게 바꿨는지*를 문장으로 엮어, 읽는 사람이 소설처럼 따라오게 한다.
- **날짜와 대상(브랜치/커밋)을 문서 상단에 명시.** 나중에 신선도를 판단할 수 있게.
- **갱신은 덮어쓰기가 아니라 append.** 기존 결정이 번복됐으면 `## 후속 (날짜)` 로 경위를 남긴다(healthcare 관례).
- 한 번 대화로 끝날 잡담·임시 판단은 위키에 남기지 않는다. 이후 작업에서도 참고할 개념·결정일 때만 남긴다.
